# P1.3 — DB Pool Saturation Observability

**Date:** 2026-09-04. Pure observability — no pool size, timeout, or query
behavior changed. `db_queries_total` (P0.5-era) stays unchanged too.

## Why this, specifically

The load-test campaign's own finding (MS-002, and independently the P0
booking-path remediation) established that **`pg_stat_activity` cannot see
pool exhaustion**: at collapse it showed every connection as `idle in
transaction` or `active`, never "waiting" — because the wait happens
entirely inside the Node process, before a connection request even reaches
Postgres. `pg-pool`'s own in-process counters (`totalCount`, `idleCount`,
`waitingCount`) are the only place that number exists. This phase exposes
them as Prometheus gauges rather than adding a new distinct measurement
mechanism.

## What was added

- **`src/metrics/metrics.service.ts`** — three new gauges: `db_pool_total`,
  `db_pool_idle`, `db_pool_waiting`, and one setter,
  `setDbPoolStats({total, idle, waiting})`. No labels (one process = one
  pool = one scrape target; the label-bearing `db_queries_total` counter
  already covers the "which route" question — this is process-wide pool
  state).
- **`src/metrics/db-pool-metrics.service.ts`** (new) — samples
  `dataSource.driver.master` (the underlying `pg-pool` instance) on a
  configurable interval (`DB_POOL_METRICS_POLL_MS`, default 15s — a cheap
  in-process property read, no query, so no reason to poll it as
  conservatively as the DLQ/queue-depth pollers) and pushes the three
  gauges. Registered in `MetricsModule` (`@Global()`), same placement
  rationale as `SchemaGuardCatalogService` in `SchemaGuardModule` (P0.5):
  cross-cutting, both process roots have their own pool, so one
  registration covers both without either needing its own wiring.
- **Rate-limited warning**, not a per-sample log line: fires only once
  `waiting > 0` on 3 consecutive samples (sustained, not a blip), then at
  most once per 5-minute cooldown while it stays sustained — a genuinely
  saturated pool gets one fresh reminder per window, not one line every 15
  seconds forever.
- **`DB_POOL_METRICS_POLL_MS`** added to `env.validation.ts` (optional,
  `min(1000)`).

## Deliberately not done

- No pool size, connection-timeout, or statement-timeout change — all
  three already have measured, documented rationale from the P0 booking
  remediation and stay untouched.
- No alerting rule / dashboard config — out of scope for this repository
  (no CI or monitoring-config pipeline exists here yet, same gap noted
  throughout this campaign).
- No live-boot + curl verification of the actual `/metrics` HTTP output.
  Judged unnecessary given the depth of unit coverage below (every code
  path the sampler can take, using real `pg-pool`-shaped objects) and that
  this is pure telemetry with zero behavioral coupling to any other part of
  the system — unlike P0.5's `SchemaGuardCatalogService`, which gates
  readiness and therefore got the full live-boot treatment.

## Verification performed

- **`db-pool-metrics.service.spec.ts`** (new, 9 tests): gauges set from a
  real `pg-pool`-shaped object's `totalCount`/`idleCount`/`waitingCount`
  getters; no warning on a single blip; warning fires exactly once after 3
  consecutive sustained samples, naming the real waiting count; the
  consecutive counter resets the moment a sample shows `waiting = 0`;
  cooldown prevents repeating the warning every sample while still
  sustained; never throws when the pool is `undefined` (driver not yet
  initialized) or when reading `dataSource.driver` itself throws; honors a
  configurable poll interval from `ConfigService` rather than a hardcoded
  one.
- **`metrics.service.spec.ts`** (+2 tests): the three gauges render
  correctly from one `setDbPoolStats` call; confirmed to be gauges (latest
  value), not counters (no accumulation) — a later `waiting: 0` call
  correctly overwrites an earlier `waiting: 8`.
- Typecheck: identical to the confirmed cross-phase baseline (19
  pre-existing errors, zero new).
- Lint: zero new issues (the two new files are fully clean; the touched
  existing files' flagged lines were verified, by position, to be
  pre-existing and unrelated).
- Full unit suite: the same 4 pre-existing failing suites, nothing new.

## Production changes required

None. `DB_POOL_METRICS_POLL_MS` is optional with a sane default; an
operator wanting a different sample rate can set it, but nothing requires
that for this to work.
