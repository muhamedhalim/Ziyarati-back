# P0.3 — Integrity guard matrix

**Date:** 2026-09-03 · **One row per critical guard**, per P0.3 RULE 2.
**Source of truth:** `pg_catalog` on four live databases, read 2026-09-03 —
not the `migrations` table, not entity metadata, not the P0.2 documents.

43 objects whose loss changes what PostgreSQL will ACCEPT. Performance-only
indexes are out of scope by RULE 13 (losing one costs latency, not
correctness) and are summarised in §4 rather than listed.

## Legend

| column | meaning |
|---|---|
| **sev** | P0 = loss corrupts money, identity or externally-visible state · P1 = loss corrupts business data |
| **owner** | `mig` the migration that creates it · `boot` an `OnApplicationBootstrap` `CREATE … IF NOT EXISTS` that re-creates it · `entity` TypeORM entity metadata |
| **sync** | does it survive a `TYPEORM_SYNCHRONIZE=true` boot? **DROPPED** = no. Measured, not inferred (P0.2). |
| **e2e / t2 / perf / dev** | state in that live database, read 2026-09-03. `✓` present under its canonical name · `~` **the rule is enforced, under a TypeORM hash name** (the synchronizer renames what it recreates from entity metadata) · **`✗`** absent — PostgreSQL is not enforcing this rule at all |
| **conflicts** | rows ALREADY violating the rule, worst across the four databases. `0` = the guard is installable by migration alone. `>0` = **BLOCKED**: `CREATE UNIQUE INDEX` will fail until a human decides which rows are real |

`test/setup-e2e-db.js`, and the only local database at 43/43. Production is
built the same way and is *expected* to match it — **expected, not verified**:

## 3. Repair strategy, lock and rollback per DDL form

All 43 guards, grouped by the DDL form that installs one. The form — not the
guard's importance — decides what installing it costs, and whether it can be
done without blocking traffic. These are PostgreSQL facts, not estimates.

| DDL form | guards | lock taken | duration | rollback |
|---|---|---|---|---|
| `ALTER TABLE ... ADD CONSTRAINT ... EXCLUDE USING gist` | 1 | ACCESS EXCLUSIVE, full build — no CONCURRENTLY, no NOT VALID form exists | measured 15.16 s on 900,000 rows (P0.1) | DROP CONSTRAINT — instant, no data change |
| `CREATE UNIQUE INDEX CONCURRENTLY` | 40 | SHARE UPDATE EXCLUSIVE — does NOT block reads or writes | two scans; proportional to table size. Cannot run inside a transaction block, so the migration must set `transaction = false` | DROP INDEX CONCURRENTLY — instant, no data change. A failed build leaves an INVALID index: drop it and retry |
| `ADD CONSTRAINT ... CHECK ... NOT VALID, then VALIDATE CONSTRAINT` | 1 | brief ACCESS EXCLUSIVE (no scan), then SHARE UPDATE EXCLUSIVE for the scan — writers are not blocked | the VALIDATE scan is proportional to table size; it is interruptible | DROP CONSTRAINT — instant, no data change |
| `CREATE UNIQUE INDEX CONCURRENTLY, then ADD CONSTRAINT ... UNIQUE USING INDEX` | 1 | no write block during the build; brief ACCESS EXCLUSIVE to attach it | two scans; proportional to table size | DROP CONSTRAINT — instant, no data change |

**The one that cannot be made online:** `appointments_no_overlap`. PostgreSQL
offers no `CONCURRENTLY` and no `NOT VALID` form for an EXCLUDE constraint,
so installing it always holds ACCESS EXCLUSIVE for the full build — every
read and write on `appointments` waits. P0.1 measured **15.16 s on 900,000
rows**. Plan a maintenance window sized from the production row count, and
set a `lock_timeout` so the attempt fails fast rather than queueing behind a
long transaction and blocking the table indefinitely.

## 4. Out of scope by RULE 13 — performance indexes

A synchronize boot also drops **56 performance indexes** (P0.2). They are
counted, not listed, and P0.3 restores none of them: RULE 13 permits
restoring only indexes proven necessary, and no measurement in this phase
establishes that for any individual one. They return automatically when a
database is rebuilt from the migration chain, which is the recommended
repair anyway.

Classification of the 43 above, per RULE 13:

| class | count | note |
|---|---|---|
| integrity only | 3 | CHECK / UNIQUE / EXCLUDE constraints — no query serves them |
| integrity **and** query performance | 40 | every unique INDEX is also a lookup path; restoring it is never a latency regression |
| obsolete | 0 | none found — every guard in this matrix has a live caller |
