# P0.3 — Database schema integrity remediation plan

**Date:** 2026-09-03
**Phase:** remediation design + controlled implementation.
**Source of truth:** `pg_catalog` on five live databases, read this date.
**Production:** still **NOT INSPECTED** — see §12.

---

## 1. Executive summary

P0.1 found one destroyed integrity guard. P0.2 measured the mechanism and found
32. P0.3 asks what to actually do about it, and implements the parts that are
safe to implement now.

**The three things worth knowing:**

1. **The self-locking failure P0.2 predicted has already happened.** On the dev
   database, `subscription_usage` holds **189 excess rows** across 17
   tenant-months, so `UQ_subscription_usage_tenant_period_unsubscribed` can
   never be installed until a human decides which rows are real. The complete
   causal chain is verified end to end (P03-001): synchronize dropped a column,
   206 usage rows lost their billing link, they all fell under the guard's
   predicate, the guard was dropped in the same boot, the idempotent upsert
   stopped conflicting, duplicates accumulated, and the door closed. It is the
   **only** data conflict in 172 guard × database checks — every other missing
   guard is installable by migration alone.

2. **Three bootstraps were deleting customer data on every boot, in every
   environment including production**, choosing the survivor by physical row
   location, and reporting nothing. Fixed (P03-002). On identical test data the
   old code silently destroyed one patient message; the new code destroys none
   and emits one ERROR plus a degraded readiness probe.

3. **`NODE_ENV=production` was never the real boundary.** It does not protect a
   staging, QA, demo or restored-from-backup database booted as `development`,
   which is where one synchronize boot costs 178 DROP INDEX / 120 DROP
   CONSTRAINT / 23 DROP COLUMN. A populated `migrations` table is the precise
   signal, and the factory now refuses on it (P03-013), verified against all
   five real databases.

**What is NOT done, deliberately:** no data repaired, no FK migration written,
no production change. §7 says why each, and what would unblock it.

**One number is corrected.** P0.2's environment matrix compared guards by NAME.
TypeORM renames what it recreates, so five guards on dev and two on perf are
enforced under hash names. Dev is 20/43, not 15/43; perf is 26/43, not 24/43.
Every P0 count is unchanged, so no conclusion moves (P03-005).

## 3. Root causes

Not "synchronize is on". That is the trigger. The causes are structural:

| # | root cause | consequence | addressed by |
|---|---|---|---|
| **R1** | **Entity metadata is not the schema.** TypeORM's synchronizer drops every object it cannot derive from entity metadata, matched by name. Partial unique indexes, CHECK constraints, EXCLUDE constraints and raw-SQL tables are invisible to it. | 32 integrity guards + 23 columns destroyed per boot | P03-013 (refuse on a migrated DB); the P0.1 `@Exclusion` precedent for individual objects |
| **R2** | **Survival was an accident of module ownership.** An object survives iff it is in entity metadata OR re-created by some module's `OnApplicationBootstrap`. Refund idempotency has a bootstrap; *purchase* idempotency does not. Nothing about importance decides it. | arbitrary coverage | §5 — bootstraps now declare criticality, and the gap is visible instead of silent |
| **R3** | **One failure policy for statements with nothing in common.** A missing money-idempotency guard and a missing dashboard index produced the identical one-line `warn`. | a missing guard in production announces itself as a warning nobody reads | P03-002 — `required` vs `optional`, ERROR + degraded readiness |
| **R4** | **Bootstraps repaired data to make DDL succeed.** Three unconditional `DELETE`s, survivor chosen by `ctid`. | customer messages destroyed, silently, on every boot | P03-002 — count and refuse |
| **R5** | **The production guard keyed on the wrong signal.** `NODE_ENV` does not identify a persistent database. | staging/QA/restored backups unprotected | P03-013 |
| **R6** | **Nothing tested any of it.** `typeorm.config.spec.ts` had 14 cases and none for the guard. No test asserted any guard exists in PostgreSQL. | every property above was one refactor from silently regressing | §8 |

## 5. Canonical schema strategy

**One rule: the migration chain owns the schema. Entity metadata describes what
the ORM needs to read and write, and is not authoritative.**

Concretely, per RULE 4, every integrity object is classified:

| class | meaning | count | examples |
|---|---|---|---|
| **A — migration-owned, bootstrap unnecessary** | the canonical form. The migration creates it; nothing re-creates it at runtime | **30** of 43 | `UQ_resource_purchases_tenant_idempotency`, `uq_user_email_global`, `ck_user_email_lowercase`, every `integration_*` replay guard |
| **B — migration-owned + runtime verification** | migration creates it; a bootstrap re-asserts it idempotently and now **reports** rather than silently succeeding | **13** of 43 | `uq_refund_idem`, `uq_txn_webhook_event`, `uq_message_wa_id`, `uq_message_status`, `uq_ai_tool_call_idem` |
| **C — runtime-created by design** | genuinely belongs at runtime; documented exception | 2 services | `PgVectorBootstrapService`, `AiMemoryVectorService` — they create `vector`-typed sidecar tables that TypeORM must never manage, and degrade to a documented keyword-search fallback when pgvector is unavailable. Left untouched. |

Every one of the 43 is created by a migration — verified by reading the
migrations, not by trusting the naming. (The attribution scan initially missed
`UQ_support_tickets_ticket_number` because it is declared inline inside
`CREATE TABLE` in `1730003000000-SupportTickets.ts` rather than as a separate
statement. Checked by hand; it is there.) **So class A is already the norm, and
the 13 in class B are the exception, not the rule.**

**Class B is not "belt and braces for its own sake."** These bootstraps exist
because dev skips migrations, and until the local databases are rebuilt they are
the only thing installing those guards there. Once every environment is
migrations-owned, class B collapses into class A and the bootstraps can be
deleted — that is the end state, not this phase.

**The exceptions, documented as RULE 4 requires:** the two class-C services, and
the six raw-SQL entity-less tables (`settlement_adjustments`,
`free_access_overrides`, `tenant_entitlement_ledger`, `tenant_metric_credits`,
`ai_kb_embeddings`, `ai_memory_embeddings`). Those six were deliberately given no
entity *precisely to dodge synchronize* — their own docstrings say so. That
decision cost them their tenant foreign keys (§6.4), which is a second-order
cost of R1 rather than an independent design choice.

## 6. Remediation, per area

### 6.1 Eliminating synchronize dependence — **IMPLEMENTED**

Three layers, in order of how much they can see:

1. `NODE_ENV=production` + `TYPEORM_SYNCHRONIZE=true` → throws. Pre-existing;
   now **tested** (6 unit cases, api and worker).
2. An **unrecognised** `NODE_ENV` → treated as production, so it throws too.
   New; closes SCHEMA-007's blind spot at the synchronize layer as well as the
   TLS one.
3. Any `NODE_ENV`, if `public.migrations` holds a row → **refuses to boot**,
   naming the count and offering three explicit ways forward. New; this is the
   layer that covers staging, QA, demos and restored backups.

Layer 3 fails **open** on an unreachable database on purpose: the DataSource
that follows reports the real connection error, which beats this check guessing.

**Local impact, stated plainly.** Dev has 118 migrations, so layer 3 fires. The
obvious workaround (`TYPEORM_SYNCHRONIZE=false`) does **not** work either —
P03-004 measured the boot failing on the first pending migration. The tracked
`.env` therefore sets `TYPEORM_SYNCHRONIZE_ALLOW_MIGRATED_DB=true` with a
comment block explaining exactly what is being accepted, so `npm run start`
behaves as it did before while the protection stays armed everywhere else. That
is a holding position, not the answer; the answer is §6.2.

### 6.2 Repairing a damaged database — **REBUILD IS THE ONLY PATH**

Measured, on a clone, never on dev:

```
clone of ziyarati (118/133 migrations)              20 / 43 enforced, 7 P0 absent
  └─ node dist/src/migrate.js run
     → FAILS: PatientActionLinks1730063000000,
              relation "patient_action_links" already exists
  └─ force past that one migration, run the other 14
                                                     23 / 43 enforced, 5 P0 absent
```

Neither safe (the boot fails) nor sufficient (still CRITICAL). Exactly **one**
migration collides, which is good news — the incompatibility is narrow — but a
migration chain that aborts is not a conversion path.

**The rebuild, which is how `ziyarati_e2e` reaches 43/43:**

```bash
createdb ziyarati_v2
DATABASE_URL=postgres://postgres:postgres@127.0.0.1:5433/ziyarati_v2 \
  node dist/src/migrate.js run          # 133 migrations from empty
npm run seed
# point DATABASE_URL at ziyarati_v2, set TYPEORM_SYNCHRONIZE=false,
# and delete TYPEORM_SYNCHRONIZE_ALLOW_MIGRATED_DB
```

Not performed here: it discards the data in `ziyarati`, which is not a decision
to make on someone's behalf.

### 6.3 Foreign-key canonicalisation — **DESIGNED, NOT MIGRATED**

The divergence is **6 + 6**, not 10 + 10 (P03-007). Four of the twenty are the
same logical FK under a renamed column or with a stripped referential action.

**Canonical direction, derived from the code:**

| group | canonical answer | why |
|---|---|---|
| 6 FKs present only in the synchronize-built schema | **adopt them** — the migration chain should create them | all six are declared `@ManyToOne` in entity metadata. The entities intend the relationship; no migration ever created it |
| 6 FKs present only in the canonical schema | **keep them** — the entities are simply under-specified | all six are plain `@Column({type:'uuid'})`. `PatientActionLink`'s docstring proves intent: *"`waitlist_offer` has no FK constraint here: `waitlist_offers` does not exist until T156, which adds the constraint once its table exists"* |
| the referential actions | **canonical wins**: tenant deletion CASCADEs on `customer_segments` and `support_tickets` | this is the sharpest edge — a tenant-deletion routine rehearsed locally behaves differently in production, silently and destructively |

**Two of the six adoptions need a measurement first, not a migration:**
`ai_execution_metrics` and `ai_memories` are high-volume append-only telemetry.
A foreign key adds a lookup on every insert. RULE 13 forbids adding anything on
intuition, so those two stay open pending a write-cost measurement.

**Not migrated in this phase** because the right sequence is: inspect production
→ learn which of the twelve it actually has → write only the migrations it needs.
Writing them now would be guessing at the starting state.

### 6.4 Tenant isolation — **TRIAGED**

15 tenant-scoped tables have no FK to `tenants` in the canonical schema (P0.2
said 13; the two pgvector sidecars are the difference, and they are
bootstrap-created). Triaged per RULE 7:

| group | tables | recommendation |
|---|---|---|
| **structurally impossible today** | `subscription_invoices`, `subscription_usage` | the column is `character varying`, not `uuid` (P03-006). A FK needs a table rewrite first. **Highest-value fix in this group** — these are billing tables |
| **append-only telemetry — measure before adding** | `ai_execution_metrics`, `ai_tool_calls`, `email_logs`, `verification_audit_logs`, `admin_notifications` | a FK costs a lookup per insert on the hottest write paths. Also: `verification_audit_logs` already has **6 orphaned rows** on dev, so adding one would abort until they are resolved — and cascading an audit trail away with its tenant may be the wrong semantics anyway |
| **raw-SQL tables that dodged synchronize** | `settlement_adjustments`, `free_access_overrides`, `tenant_counters` | these already carry a tenant FK in their bootstrap DDL where one was wanted (`tenant_entitlement_ledger` has `ON DELETE CASCADE`); the gap is inconsistency, not absence of intent. Align them |
| **entity-declared, migration missing** | `workflows`, `workflow_runs`, `ai_memories` | same six as §6.3. Adopt |
| **pgvector sidecars** | `ai_kb_embeddings`, `ai_memory_embeddings` | class C by design. Leave |

Data check across all four databases: `0` orphans everywhere except the two dev
cases above. So eleven of the fifteen could take a FK today with no data work.

### 6.5 Fail-closed bootstraps — **IMPLEMENTED**

Every bootstrap statement now declares its intent:

- **`required`** — a DB-enforced integrity guard. Failure logs at **ERROR** with
  the guard name, the Postgres message and what to run next, and marks readiness
  **degraded**.
- **`optional`** — a performance index. Failure logs at `warn`, exactly as
  before.
- **`blocked`** — a new outcome: conflicting rows already exist, so the guard was
  not attempted. Reports the count and the business meaning, changes nothing.

**Nothing throws.** RULE 5 asks for readiness failure over corruption, and warns
against introducing an outage. Making a bootstrap fatal turns "one index is
missing" into "the clinic cannot take bookings", and would make the
self-locking case an unrecoverable crash loop. So *noticing* is separated from
*stopping*:

| surface | behaviour |
|---|---|
| application log | ERROR per failed required guard, with full detail |
| `GET /system/health/readiness` | `status: "degraded"`, `schemaGuards: { status, requiredChecked, requiredFailed }` — **counts only** |
| HTTP status of that route | 200 by default; **503** when `SCHEMA_GUARD_FAIL_READINESS=true` |

The readiness payload deliberately carries no object name, table name or
PostgreSQL message: the route is `@Public()`, and naming a missing uniqueness
guard would tell an anonymous caller exactly which duplicate to attempt. The
Docker `HEALTHCHECK` probes *liveness*, not this route, so a degraded readiness
never causes a restart loop.

### 6.6 Performance — **OUT OF SCOPE (RULE 13)**

56 performance indexes are lost per synchronize boot. Counted, not restored: no
measurement in this phase establishes that any individual one is necessary, and
RULE 13 permits restoring only those proven so. They return automatically on a
rebuild, which is the recommended repair anyway.

## 9. Migration strategy and safety (RULE 12)

Full per-guard detail in `P0.3_INTEGRITY_GUARD_MATRIX.md` §3. The rules that
matter:

| DDL form | lock | online? | rollback |
|---|---|---|---|
| `CREATE UNIQUE INDEX CONCURRENTLY` | SHARE UPDATE EXCLUSIVE | **yes** — no reads or writes blocked. Two scans. Cannot run in a transaction, so the migration must set `transaction = false`. A failed build leaves an **INVALID** index: drop and retry | `DROP INDEX CONCURRENTLY` — instant, no data change |
| `ADD CONSTRAINT ... UNIQUE USING INDEX` | brief ACCESS EXCLUSIVE to attach | **yes**, if the index was built concurrently first | `DROP CONSTRAINT` — instant |
| `ADD CONSTRAINT ... CHECK ... NOT VALID` then `VALIDATE` | brief ACCESS EXCLUSIVE (no scan), then SHARE UPDATE EXCLUSIVE | **yes** — writers are not blocked during validation | `DROP CONSTRAINT` — instant |
| `ADD CONSTRAINT ... FOREIGN KEY ... NOT VALID` then `VALIDATE` | as above, on **both** tables | **yes** | `DROP CONSTRAINT` — instant |
| **`ADD CONSTRAINT ... EXCLUDE USING gist`** | **ACCESS EXCLUSIVE for the full build** | **NO.** PostgreSQL offers no `CONCURRENTLY` and no `NOT VALID` form for an exclusion constraint | `DROP CONSTRAINT` — instant |
| `ALTER COLUMN ... TYPE uuid` | **ACCESS EXCLUSIVE, full table rewrite** | **NO** | restore from backup — a rewrite is not reversible in place |

**The one that needs a window:** `appointments_no_overlap`. P0.1 measured
**15.16 s on 900,000 rows** holding ACCESS EXCLUSIVE — every read and write on
`appointments` waits. Size the window from the production row count, and set
`lock_timeout` so the attempt fails fast instead of queueing behind a long
transaction and blocking the table indefinitely.

**Every repair migration must follow the P0.1 `AppointmentNoOverlapRepair`
pattern:** idempotent early return if the object already exists; a conflict
pre-check that counts and `RAISE EXCEPTION`s with the counts **in the MESSAGE**
(node-postgres surfaces only `error.message` through `QueryFailedError`, so
`DETAIL` and `HINT` are invisible to the CLI); no deletion, ever; a post-condition
assert. And "it succeeded locally" is not evidence of safety — the local
databases are missing up to 23 guards and hold at most 900,000 rows.

## 12. Production verification

Production has **never been inspected** — not in P0.1, not in P0.2, not here.
Everything this plan says about it is inference from the fact that it is built
by the same migration chain as `ziyarati_e2e`.

One command converts that inference into a fact:

```bash
psql "$DATABASE_URL" -f tests/load/reports/P0.3_PRODUCTION_VERIFICATION.sql
```

It reads `pg_catalog` and `information_schema`, and in §5 counts rows in
application tables. It writes nothing — no INSERT, UPDATE, DELETE or persistent
DDL — and creates three session-local TEMP views. §5 is the expensive part
(aggregates over the backing tables); stop after §4 to skip it, or run the whole
thing against a read replica.

Validated in both directions before shipping: `P03_STATUS=ENFORCED … TOTAL=43`
on the clean reference database, `P03_STATUS=CRITICAL … P0_FAIL=7` on the
synchronize-damaged dev database, and `BLOCKED … 189 excess rows` correctly
identified on the one guard that has a data conflict.
