# P0.3 — Findings

**Date:** 2026-09-03 · **Phase:** remediation design + controlled implementation.
**Source of truth:** `pg_catalog` on five live databases, read this date — not
the `migrations` table, not entity metadata, not the P0.2 documents.

**What was changed:** application code, configuration and tests only. **No
production database was touched. No row was deleted, merged or rewritten in any
database.** The only databases written to were `p03_verify`, `p03_virgin`,
`p03_devclone` and the throwaway databases the integration tests create and
drop, all created for this phase.

Findings are numbered `P03-nnn`. Where one resolves or refines a P0.2 finding,
that is stated. Fixes implemented in this phase are marked **FIXED**; everything
else is documented for a later decision, per the implementation boundary.

## P03-001 — The self-locking failure mode is not hypothetical: it has already happened

**Severity: Critical** (dev today; the same mechanism reaches production)
**Refines:** SCHEMA-004, which predicted this. **Not fixed — needs a business decision.**

P0.2 argued that `CREATE UNIQUE INDEX IF NOT EXISTS` fails once duplicates
exist, so "guard missing → duplicates accumulate → the guard can never be
installed again" is a one-way door. P0.3 went looking for an instance and found
one, on the dev database, with the complete causal chain intact:

```
subscription_usage:  207 rows,  206 with subscription_id IS NULL,
                     17 distinct (tenant_id, period_month) keys,
                     189 EXCESS rows.   Worst single key: 180 rows.
UQ_subscription_usage_tenant_period_unsubscribed:  ABSENT.
```

The chain, each step verified against the catalog:

1. **The column was destroyed.** `subscription_usage.subscription_id` sits at
   ordinal position **3** in the canonical schema and position **10** in dev,
   with position 3 missing entirely — the physical signature of `DROP COLUMN`
   followed by `ADD` (SCHEMA-002 recorded this statement; P0.3 confirms the
   result). The re-added column is empty.
2. **206 usage rows lost their billing link.** Dev holds 14 subscriptions and
   exactly **1** usage row still linked to one. Those rows are not
   subscription-less tenants; they are orphans made by the column wipe.
3. **They therefore all match the guard's predicate** (`WHERE subscription_id
   IS NULL`), which was written for a genuinely different case — a clinic on a
   super-admin grant with no plan.
4. **The guard itself was dropped** in the same boot (it is migration-only, so
   nothing re-creates it).
5. **The upsert's `ON CONFLICT DO NOTHING` stopped conflicting.** 180 duplicate
   rows accumulated for one tenant-month.
6. **The door closed.** `CREATE UNIQUE INDEX IF NOT EXISTS` now fails on this
   table permanently. No boot, no migration and no rebuild-in-place can install
   the guard while those rows exist.

**Business impact.** Per-tenant monthly usage is no longer single-valued for 17
tenant-months. Whatever reads those counters — quota enforcement, the usage
breakdown, retroactive billing — is reading one of 180 rows or a sum of them.
The migration that created the guard says so in its own docstring: *"the partial
index below restores exactly one row per tenant-month, which is what makes the
idempotent `ON CONFLICT DO NOTHING` upsert safe on that path too."*

**Why nothing was repaired.** RULE 9. Choosing which of 180 usage rows is the
real one, or how to combine them, is a business decision with billing
consequences. The three defensible options and their trade-offs are set out in
`P0.3_REPAIR_RUNBOOK.md` §3. **This is the one finding in P0.3 that is blocked
on a human.**

**Scope.** This is the ONLY data conflict found. All 43 guards were checked
against all four live databases — 172 checks — and every other one is `0
conflicts`. Every other missing guard is installable by migration alone.

**Verification.**
```bash
psql "$DATABASE_URL" -f tests/load/reports/P0.3_PRODUCTION_VERIFICATION.sql   # §5
```

## P03-002 — Three bootstraps deleted application data on every boot, in every environment including production — **FIXED**

**Severity: High** · **Flags:** `BOOTSTRAP_DEPENDENCY`

Two `OnApplicationBootstrap` services ran three unconditional `DELETE`
statements on every application start, in every environment, production
included. They are the exact anti-pattern RULE 9 forbids — "fix the conflict by
choosing an arbitrary row" — and they were doing it automatically, forever.

```sql
-- conversations-schema.bootstrap.ts
DELETE FROM messages a USING messages b
 WHERE a.ctid > b.ctid AND a."tenantId" = b."tenantId"
   AND a.wa_message_id = b.wa_message_id AND a.wa_message_id IS NOT NULL;

DELETE FROM message_status_logs a USING message_status_logs b
 WHERE a.ctid > b.ctid AND a."messageId" = b."messageId" AND a.status = b.status;

-- analytics-schema.bootstrap.ts
DELETE FROM dashboard_metrics a USING dashboard_metrics b
 WHERE a.ctid < b.ctid AND a."tenantId" = b."tenantId"
   AND a.metric_key = b.metric_key AND a.period IS NOT DISTINCT FROM b.period;
```

Four things were wrong:

1. **They destroy customer data** — `messages` rows are patient conversations —
   to make a `CREATE UNIQUE INDEX` succeed.
2. **The survivor is chosen by `ctid`**, the row's physical location on disk.
   PostgreSQL changes it on any `UPDATE` and on `VACUUM FULL`, so which message
   survived was not deterministic. The two files even disagree on the direction
   (`>` versus `<`).
3. **They fail soft**, so the number of rows deleted was never reported
   anywhere — not at `warn`, not at all.
4. **They contradict the analytics one's own intent**: it compared `period IS
   NOT DISTINCT FROM`, treating two NULL periods as a collision, while the
   unique index it was clearing the way for treats NULLs as distinct. It could
   delete rows that were never in conflict.

**Measured, on identical data.** A disposable database with two `messages` rows
sharing `(tenantId, wa_message_id)`:

| | rows left | guard installed | reported |
|---|---|---|---|
| old code | **1** — one message silently destroyed | yes | nothing |
| new code | **2** — nothing touched | no | one ERROR line, readiness `degraded` |

**The fix.** Each `DELETE` is replaced by a count-and-report pre-check that
reproduces PostgreSQL's own uniqueness semantics (NULL keys are exempt, so it
cannot report a phantom conflict). When conflicts exist the index is not
attempted; the guard is reported `blocked` with the exact count and what it
means, at `error`, and readiness reports `degraded`. Verified end to end against
a real boot — see §Evidence.

## P03-003 — The append-only ledger guard could be dropped and not restored, silently — **FIXED**

**Severity: High**

`PaymentsSchemaBootstrap` recreated the `transactions` immutability trigger as
two independent fail-soft statements:

```ts
await this.run('transactions immutability trigger (drop)',
  `DROP TRIGGER IF EXISTS transactions_no_mutate ON transactions`);
await this.run('transactions immutability trigger (create)',
  `CREATE TRIGGER transactions_no_mutate ...`);
```

The `DROP` always succeeds. Any failure of the `CREATE` — a lock timeout, a
permissions change, a transient error — therefore left the transactions ledger
with **no append-only protection at all**, and said so in one `warn` line. The
bootstrap could make the database strictly less protected than it found it, on
a table whose whole design premise is that it is immutable.

**The fix.** Both statements now run inside one `DO $do$ … END $do$` block, so
they are atomic: either the trigger is replaced, or the old one is still
standing. The statement is classified `required`, so a failure is an ERROR.

## P03-004 — A synchronize-built database cannot be converted to migrations-first. Rebuild is the only path.

**Severity: High** (blocks the obvious remediation) · **Refines:** SCHEMA-001 remediation 1, SCHEMA-009

P0.2 recommended setting `TYPEORM_SYNCHRONIZE=false` and noted that re-running
recorded migrations repairs nothing. P0.3 tested the actual conversion on a
**clone** of the dev database (never on dev itself) and found it is worse than
"repairs nothing" — it does not even complete:

```
p03_devclone (= ziyarati, 118 of 133 migrations recorded)
$ node dist/src/migrate.js run
Migration "PatientActionLinks1730063000000" failed, error:
  relation "patient_action_links" already exists
[migrate] FAILED
```

Synchronize had already created that table from entity metadata; the migration
issues a bare `CREATE TABLE`. **The boot fails.** Not degraded — failed.

Forcing past it (marking that one migration applied, which is what an operator
under pressure would do) lets the other 14 apply, and produces:

| | guards enforced | verdict |
|---|---|---|
| fresh clone of dev, nothing run | 20 / 43 | CRITICAL, **7** P0 absent |
| after forcing the chain through | **23 / 43** | **still CRITICAL, 5 P0 absent** |

Three guards recovered; two of seven P0 gaps closed. Sixteen P1 guards and five
P0 guards remain absent, and no further migration can install them, because they
are already recorded as applied (P0.1 DRIFT-002).

So the conversion is neither safe nor sufficient. It also silently skips
whatever else `PatientActionLinks` did — the clone ends with 4 indexes on
`patient_action_links` where canonical has 5.

**Only ONE migration collides**, which is genuinely good news for the runbook:
the incompatibility is narrow and identifiable, not pervasive.

**Consequence for the plan.** The only route from a synchronize-built database
to a correct one is **rebuild from empty via the migration chain**, exactly as
`test/setup-e2e-db.js` does for `ziyarati_e2e` — the one local database at
43/43. That is a destructive operation on developer data, so P0.3 documents it
and does not perform it.

## P03-005 — P0.2's per-database guard counts were name-based, and understated enforcement by up to five guards — **CORRECTED**

**Severity: Medium (accuracy)** · **Corrects:** SCHEMA-009, SCHEMA-001's environment matrix

TypeORM's synchronizer renames every index it recreates from entity metadata to
`IDX_<28 hex>`. A guard declared on an entity is therefore dropped and
immediately re-created under a hash name: **the rule survives, the name does
not.** P0.2's verification script matched by name and counted those as absent.

Comparing index *shape* instead — uniqueness, table, columns, predicate:

| database | P0.2 said | actually enforced | of which renamed |
|---|---|---|---|
| `ziyarati_e2e` | 43 / 43 | 43 / 43 | 0 |
| `ziyarati_perf_t2` | 33 / 43 | 33 / 43 | 0 |
| `ziyarati_perf` | 24 / 43 | **26 / 43** | 2 |
| `ziyarati` (dev) | **15 / 43** | **20 / 43** | 5 |

Example: dev has no `UQ_customers_tenant_email`, but it does have
`IDX_fbd833f031b18a738d3fb881ea` —
`UNIQUE ("tenantId", email) WHERE (deleted_at IS NULL)`, byte-identical.

**Every P0 count is unchanged** (none of the renamed survivors is P0), so no
conclusion in P0.1 or P0.2 moves: dev is still CRITICAL with 7 P0 guards absent,
and the synchronize mechanism is still destructive. The number was wrong and is
corrected here.

**Why it matters operationally:** a false `FAIL` on production would send an
operator to install a guard that already exists — under a different name, which
would then fail as a duplicate index or create a redundant one.
`P0.3_PRODUCTION_VERIFICATION.sql` reports these as `ENFORCED_RENAMED`, a
verdict of its own, with the name actually in use.

**Cross-validated:** two independent implementations (a Node shape-normaliser
and the SQL script's `p03_shape` view) agree exactly on all four databases.

## P03-006 — Two billing tables store the tenant key as `character varying`, so a tenant foreign key is structurally impossible

**Severity: Medium** · **Refines:** SCHEMA-006 · **Not fixed — needs a decision + a table rewrite**

`subscription_invoices.tenant_id` and `subscription_usage.tenant_id` are
`character varying`. `tenants.id` is `uuid`. This is true on **all three**
databases checked including the canonical reference — so it is not drift, it is
what the migration chain builds, and production has it too.

Three consequences:

1. **`ADD CONSTRAINT ... FOREIGN KEY` cannot be written for these two tables**
   at all. Attempting it gives `foreign key constraint cannot be implemented:
   Key columns are of incompatible types`. Any tenant-FK remediation must first
   `ALTER COLUMN ... TYPE uuid USING tenant_id::uuid`, which rewrites the table
   under ACCESS EXCLUSIVE.
2. **Comparisons are string comparisons.** Two different spellings of the same
   UUID — different case, or braced — are different tenants to PostgreSQL. On
   the four databases checked the data is clean (0 non-lowercase, 0 non-UUID-
   shaped, 0 orphans), so the hazard is latent, not realised.
3. **The application already works around it**, and says so. Four raw-SQL joins
   in `platform-usage.service.ts` cast both sides, with a comment ending *"Do
   not 'simplify' this to a bare `=`."* Those casts also make the join
   unindexable by the plain column index.

## P03-007 — The foreign-key divergence is 6+6 genuine, not 10+10

**Severity: Medium** · **Refines:** SCHEMA-005

P0.2 reported 10 FKs each way between the canonical and synchronize-built
schemas. P0.3 reproduced that exactly on the live databases (299 = 299, 10 each
way — independent confirmation of the P0.2 experiment) and then classified them.
Four of the twenty are the SAME logical FK, not distinct ones:

| appears as | reality |
|---|---|
| `clinical_entry_revisions.changedById` vs `.changed_byId` | one FK, column renamed by SCHEMA-002 |
| `customer_segments.createdById` vs `.created_byId ON DELETE SET NULL` | one FK, renamed **and** stripped of its referential action |
| `customer_segments.tenantId` (both) | present both sides; canonical has **ON DELETE CASCADE**, synchronize-built has none |
| `support_tickets.tenantId` (both) | same — canonical **CASCADE**, synchronize-built none |

Netting those out gives the real picture:

**6 exist only in the synchronize-built schema.** All six are declared
`@ManyToOne` in entity metadata and created by NO migration — so the entities
intend them and the migration chain never caught up:
`ai_execution_metrics.tenantId`, `ai_memories.tenantId`, `workflows.tenantId`,
`workflow_runs.tenantId`, `customer_notes.conversationId`,
`handover_requests.transferred_from_id`.

**6 exist only in the canonical schema.** All six are plain
`@Column({ type: 'uuid' })` on their entity — no relation, so the synchronizer
has no reason to create them: `ai_batch_items.batch_job_id` (CASCADE),
`ai_batch_items.tenant_id`, `ai_batch_jobs.tenant_id`, `api_logs.api_key_id`,
`patient_action_links.waitlist_offer`, `tenant_ai_deployments.tenant_id`.

**Canonical direction, established from the code rather than assumed:** the
migration-built schema is authoritative, *except* for the six entity-declared
FKs, which are gaps in the migration chain. Evidence that this is intent and not
oversight — `PatientActionLink`'s own docstring: *"`waitlist_offer` has no FK
constraint here: `waitlist_offers` does not exist until T156 (Phase 13), which
adds the constraint once its table exists."* The FK is deliberate; the entity
simply never declared the relation.

**The sharpest edge remains the referential action.** Deleting a tenant
**cascades** in the canonical schema (`customer_segments`, `support_tickets`) and
is **blocked** in a synchronize-built one. A tenant-deletion routine rehearsed
locally behaves differently in production — silently, and destructively.

## P03-008 — Orphaned tenant references exist in dev, in an audit table

**Severity: Medium** · **Not fixed — data, not code**

Checking all 15 tenant-scoped tables that lack a tenant FK, for rows pointing at
a `tenants.id` that does not exist:

| database | table | rows | orphans |
|---|---|---|---|
| dev | `verification_audit_logs` | 52 | **6** |
| dev | `tenant_counters` | 1 | **1** |
| dev | everything else | — | 0 |
| perf / perf_t2 / e2e | all | — | 0 |

`verification_audit_logs` is an audit trail: six of its rows record actions
against a tenant that no longer exists, and nothing in the schema prevented
that. It also means an `ADD CONSTRAINT ... FOREIGN KEY` on that column would
**fail** on this database until those rows are resolved — the same class of
blocker as P03-001, on a smaller scale.

Whether an audit log *should* carry a cascading FK is itself a design question:
cascading would delete the audit trail along with the tenant, which is often
exactly what an audit trail must not do. `ON DELETE SET NULL` or no FK plus a
documented retention policy may be the right answer. Not decided here.

## P03-009 — The integration test suite inherits `.env`, and is safe only by convention

**Severity: Low** · **Not fixed — documented**

`test/jest-integration.json` has no `setupFiles`. `test/jest-e2e.json` and
`test/jest-security.json` both load `jest-e2e.env.js`, which forces
`TYPEORM_SYNCHRONIZE=false` and repoints `DATABASE_URL` at `ziyarati_e2e`. The
integration config does neither, so every integration spec starts with the
tracked `.env` — which points at the dev database with synchronize on.

**No integration spec is actually unsafe today**: each one that touches a
database creates its own throwaway database and constructs its DataSource with
`synchronize: false` explicitly. Verified for all six existing specs and the two
added in this phase. But that is a property of every spec author remembering,
not of the configuration. The P0.3 `synchronize-guard` spec would now also
refuse to boot against a migrated database if one were used by mistake, which
narrows the exposure further.

## P03-010 — `npm run test:e2e` never rebuilds the database it asserts against

**Severity: Low** · **Not fixed — documented**

`package.json` defines `pretest:e2e:integration-platform` (which runs
`setup-e2e-db.js`) but there is no `pretest:e2e`. So `npm run test:e2e` runs
against whatever `ziyarati_e2e` currently contains. It is 43/43 today; nothing
guarantees it stays that way, and a stale e2e database is precisely how a suite
comes to pass while proving nothing about the schema it claims to exercise —
P0.2's final rule.

The new `schema-contract.int-spec.ts` closes the underlying risk differently and
more strongly: it builds a database from empty on every run, so it cannot be
fooled by a stale one.

## P03-011 — The migration CLI validated no environment at all — **FIXED**

**Severity: Medium** · **Resolves:** SCHEMA-007

`src/migrate.ts` reads `process.env` directly and runs no Joi validation, by
design. `databaseSslOptions` compared `NODE_ENV === 'production'` exactly, so
`PRODUCTION`, `prod` and `production ` (trailing space) all took the
non-production branch and returned `ssl: false` — connecting to the production
database with certificate verification entirely disabled, while succeeding
silently.

**Two fixes, deliberately layered:**

1. `isProductionEnv()` normalises (trim, lower-case) and treats anything still
   unrecognised as **production**. Getting it wrong in that direction costs a
   clear boot error in a mistyped dev environment; getting it wrong the other
   way costs an unauthenticated production database connection.
2. `migrate.ts` refuses to run at all on a `NODE_ENV` outside
   `development|production|test`, because a value the migration job does not
   recognise means the job and the application may not agree on environment
   policy at all — which is worth refusing rather than silently correcting.

The same helper now backs the synchronize guard, so an unrecognised `NODE_ENV`
refuses synchronize as well.

**Residual gap, stated rather than fixed:** an entirely *unset* `NODE_ENV` is
still treated as non-production, because Joi's own default is `development` and
the Dockerfile sets `NODE_ENV=production` explicitly. A production migration job
with no `NODE_ENV` at all would still skip certificate verification.

## P03-012 — The production synchronize guard is now tested, and so is the case it cannot see — **FIXED**

**Severity: Medium** · **Resolves:** SCHEMA-008

P0.2 verified the guard by hand and recorded that nothing pinned it. Added:

- **6 unit cases** in `src/config/typeorm.config.spec.ts`: production + `true`
  throws for the api role; the same for `worker`; production + `false` yields
  `synchronize: false` and `migrationsRun: false`; unset behaves as off;
  `TRUE`/`True`/`1`/`yes`/`on` all fail closed (the comparison is exact); and an
  unrecognised `NODE_ENV` refuses too.
- **5 integration cases** in `test/integration/synchronize-guard.int-spec.ts`,
  against real PostgreSQL, for the case `NODE_ENV` cannot see: a database with a
  populated `migrations` table.
- **7 contract cases** in `test/integration/schema-contract.int-spec.ts`, which
  build a database from empty and assert all 43 guards exist with the exact
  canonical definition, plus the extension, the append-only trigger, and that
  `appointments_no_overlap` is `contype = 'x'` and not a same-named btree index.

The contract test was verified to actually fail: injecting a non-existent P0
guard and stripping one predicate from the fixture produced exactly two
failures, naming both. A test that cannot fail proves nothing.

## P03-013 — `NODE_ENV=production` was never the real boundary; a populated `migrations` table is — **FIXED**

**Severity: High (design)** · **Extends:** SCHEMA-001

The existing guard refuses synchronize when `NODE_ENV=production`. That leaves
the genuinely dangerous middle ground completely unprotected: a staging, QA,
demo, restored-from-backup or shared-team database, provisioned by migrations
and holding real data, booted as `development`. One such boot costs 178 DROP
INDEX, 120 DROP CONSTRAINT, 23 DROP COLUMN and 28 DROP NOT NULL.

`typeOrmFactory` now probes the target before enabling synchronize and refuses
if `public.migrations` holds any row, because a database with migration history
was provisioned by the chain and every object the chain created that entity
metadata does not describe will be dropped. A database created BY synchronize
has no such table, so the ordinary local workflow is untouched. It fails **open**
on an unreachable database, deliberately: the DataSource that follows will
report the real connection error, which is more useful than this check guessing
at one.

Verified against every real database:

| database | migrations | result |
|---|---|---|
| `ziyarati` (dev) | 118 | **REFUSED** |
| `ziyarati_e2e` | 132 | **REFUSED** |
| `ziyarati_perf` | 133 | **REFUSED** |
| `ziyarati_perf_t2` | 75 | **REFUSED** |
| `p03_virgin` (never migrated) | 0 | allowed, `synchronize=true` |

**This changes local behaviour, and the change is real.** The dev database has
118 migrations, so `npm run start` would now refuse — and P03-004 shows the
obvious alternative (`TYPEORM_SYNCHRONIZE=false`) fails too. The tracked `.env`
therefore carries `TYPEORM_SYNCHRONIZE_ALLOW_MIGRATED_DB=true`, which restores
today's exact behaviour and logs a warning naming what may be dropped, with a
comment block explaining precisely what is being accepted and what the real fix
is. The protection stays armed for every other database, which is where the same
boot would be a disaster.

## Evidence

Every claim above is reproducible.

**The fail-closed bootstrap, end to end on a real database.** `p03_verify`,
built from the migration chain from empty; `uq_message_wa_id` dropped; two
`messages` rows inserted sharing `(tenantId, wa_message_id)`; the real
`dist/src/main.js` booted against it:

```
ERROR [SchemaGuard] INTEGRITY GUARD BLOCKED BY EXISTING DATA —
  "messages wa_message_id unique" (ConversationsSchemaBootstrap):
  1 conflicting row(s). Two or more rows in `messages` share
  (tenantId, wa_message_id) — the same provider message is recorded twice, so
  an at-least-once WhatsApp webhook retry is NOT being de-duplicated by the
  database. No rows were changed. Resolving this is a business decision, not an
  automatic repair — see tests/load/reports/P0.3_REPAIR_RUNBOOK.md.

GET /api/v1/system/health/readiness
{"status":"degraded","database":{"status":"up"},"redis":{"status":"up","latencyMs":2},
 "schemaGuards":{"status":"degraded","requiredChecked":21,"requiredFailed":1}}

messages after boot: 2   (old code would have left 1)
uq_message_wa_id:    absent, as it must be
```

**And the recovery path**, same database, after removing the two test rows:

```
GET /api/v1/system/health/readiness
{"status":"ok",...,"schemaGuards":{"status":"ok","requiredChecked":21,"requiredFailed":0}}
uq_message_wa_id: installed
SchemaGuard errors: 0
```

Note what the readiness payload does **not** contain: no object name, no table
name, no PostgreSQL message. That route is unauthenticated, and naming a missing
uniqueness guard there would tell an anonymous caller exactly which duplicate to
attempt. The detail goes to the log and to `SchemaGuardRegistry.failures()`,
both operator-only.
