# P0.2 — Database Schema Integrity Audit

**Date:** 2026-09-02
**Phase:** **audit only — nothing was repaired.** No constraint, index, column
or row was dropped or altered in any pre-existing database. The only database
written to was `p02_audit`, created for this audit and dropped afterwards. No
application code was changed.
**Trigger:** P0.1 proved `TYPEORM_SYNCHRONIZE=true` destroys schema objects that
entity metadata does not describe, and estimated the blast radius at "about 20
indexes". **That estimate was low by a factor of six.**

---

## 1. Answer first

A single `TYPEORM_SYNCHRONIZE=true` boot against a fully-migrated database
issues **178 `DROP INDEX`** and **120 `DROP CONSTRAINT`** statements, plus **23
`DROP COLUMN`** and **28 `ALTER COLUMN … DROP NOT NULL`**. After every module
bootstrap has finished re-creating what it can, the database has permanently
lost:

| | net loss after one boot |
|---|---|
| **UNIQUE indexes** (integrity) | **21** |
| **CHECK constraints** | **10** |
| **UNIQUE constraints** | **1** |
| performance indexes | 56 |
| foreign keys | 10 lost / 10 gained (different sets) |
| NOT NULL constraints | 29 |
| **columns (data destroyed)** | **23** |

**32 of those are integrity guards** — objects whose absence changes what the
database will accept. The rule deciding which survive is not importance; it is
whether some module happens to re-issue them at boot:

> An object survives a synchronize boot **iff** it is either declared in TypeORM
> entity metadata, or re-created by an `OnApplicationBootstrap`
> `CREATE … IF NOT EXISTS`. Nothing else survives.

That is why refund idempotency (`uq_refund_idem`, bootstrap-backed) survives
while **purchase** idempotency (`UQ_resource_purchases_tenant_idempotency`,
migration-only) does not.

**Production is not damaged by this mechanism** — `synchronize` is forced off
and is a hard boot error under `NODE_ENV=production`, verified for both the API
and worker roles (§5). **Production has still not been inspected**; only the
operator can do that, with `P0.2_PRODUCTION_VERIFICATION.sql`.

The findings that *do* reach production are different ones: bootstraps that
fail silently (SCHEMA-004), foreign keys that exist in dev and not in
production (SCHEMA-005), and 13 tenant-scoped tables with no tenant foreign key
in the canonical schema (SCHEMA-006).

---

## 2. Method

Everything below is measured on a disposable database, never inferred.

```
1. createdb p02_audit
2. node dist/src/migrate.js run                    → 133 migrations from empty
3. psql -f snapshot.sql > A                        → the canonical schema
4. boot dist/src/main, TYPEORM_SYNCHRONIZE=true    → once, the real API binary
5. psql -f snapshot.sql > B                        → after every bootstrap ran
6. diff A B, functionally (not by name)
```

Three deliberate choices:

- **The real binary, not a synthetic DataSource.** `dist/src/main` with
  `NODE_ENV=development`, i.e. exactly what `npm run start` does.
- **Functional comparison.** Synchronize renames what it re-creates
  (`IDX_<28 hex>`), so a name-based diff reports ~150 losses where the true
  figure is 77. Every index is normalised to
  `(unique?, table, method, columns, predicate)` and every constraint to
  `(type, table, definition)` before comparison.
- **Snapshot B taken twice**, eight seconds apart and again minutes later:
  byte-identical. The losses are net and final, not a startup window.

The snapshot captures indexes (with predicates and expressions), constraints of
all six types, triggers, extensions, functions, tables, and every column's
nullability and default — 4,024 lines for this schema.

**Canonical schema (133 migrations, PostgreSQL 18):** 156 tables · 454 indexes ·
297 foreign keys · 252 unique indexes · 17 CHECK · 10 UNIQUE · 1 EXCLUSION ·
1 trigger · 4 extensions.

## 3. What synchronize destroys

### 3.1 Integrity guards (32)

Listed per-object with a five-environment presence matrix in
`P0.2_SCHEMA_INVENTORY.md`. Grouped by what stops being true:

**Idempotency and replay protection** — `UQ_resource_purchases_tenant_idempotency`
(purchases charge money), `UQ_sub_invoice_webhook_event`,
`UQ_integration_inbound_events_replay`, `UQ_integration_oauth_states_state`,
`UQ_notification_logs_source_ref`, `UQ_scheduled_notifications_source_ref`,
`UQ_scheduled_notifications_provider_ref`, `UQ_campaign_recipients_provider_ref`,
`UQ_in_app_notifications_recipient_dedupe`.

**Identity** — `uq_user_email_global` and `ck_user_email_lowercase`. Losing both
together is worse than losing either: the unique index goes, *and* the
normalisation that would have made an application-level check reliable.

**Business uniqueness** — `UQ_sub_invoice_period`,
`UQ_subscription_usage_tenant_period_unsubscribed`,
`UQ_email_suppressions_tenant_email` (unsubscribe compliance),
`UQ_integration_id_map_external`/`_internal`, `UQ_integration_conflicts_open`,
`UQ_integration_sync_active`, `UQ_integration_staff_provisioning_open`,
`UQ_integration_webhook_endpoints_connection`,
`UQ_support_tickets_ticket_number`, `uq_ai_kb_source_content_hash`,
`uq_ai_batch_item_source_chunk`.

**Value constraints (10 CHECKs)** — five on `resource_purchases`
(`quantity > 0`, `total_minor > 0`, `unit_price_minor > 0`, `unit_size > 0`,
`delta_units > 0`), three on `resource_price_catalog`, one on
`subscription_plans`, plus `ck_user_email_lowercase`. Without them the database
accepts a purchase of zero units at a negative price.

### 3.2 Column data (23)

`DROP COLUMN` followed by `ADD` — **not** a rename, so the data is gone. The
worst case is a clinical audit trail:

```
ALTER TABLE "clinical_entry_revisions" DROP COLUMN "changed_byId"
ALTER TABLE "clinical_entry_revisions" ADD "changedById" uuid
ALTER TABLE "clinical_entry_revisions" DROP COLUMN "created_at"
ALTER TABLE "clinical_entry_revisions" ADD "created_at" TIMESTAMP NOT NULL DEFAULT now()
```

Who changed each clinical entry: erased. When: reset to boot time. Also
`subscription_usage.subscription_id` (the link from usage to the subscription
being billed) and the `deleted_at` columns of `clinical_entries` and
`customer_segments` — dropping and re-adding `deleted_at` **un-deletes every
soft-deleted row**. Full list in SCHEMA-002.

### 3.3 Nullability (29)

11 of them tenant keys, including every clinical table. A NULL `tenantId` is a
row belonging to no tenant. Full list in SCHEMA-003.

### 3.4 What is immune

Extensions (4/4 unchanged), the `transactions_no_mutate` trigger and its
function `trg_transactions_immutable` — TypeORM neither creates nor drops
triggers, so the append-only transaction ledger is safe from this failure mode.
Tables are never dropped; only their columns are.

## 4. What survives, and why it is not reassuring

32 objects are dropped by the synchronizer and re-created moments later by
module bootstraps issuing `CREATE … IF NOT EXISTS` — among them
`uq_refund_idem`, `uq_txn_webhook_event` and `uq_message_wa_id`, the three the
brief named. Eight files do this:

```
src/modules/payments/payments-schema.bootstrap.ts
src/modules/subscription-billing/platform-billing.bootstrap.ts
src/modules/billing-upgrades/billing-upgrade.bootstrap.ts
src/modules/analytics/analytics-schema.bootstrap.ts
src/modules/conversations/conversations-schema.bootstrap.ts
src/modules/ai/tools/ai-tool-calls.bootstrap.ts
src/modules/ai/rag/pgvector-bootstrap.service.ts
src/modules/ai-memory/ai-memory-vector.service.ts
```

Two reasons this is not comfort:

1. **Coverage is arbitrary.** These bootstraps exist because their authors
   individually noticed that dev skips migrations. Whether a given guard has one
   is a function of which module it belongs to, not of how much it matters.
2. **They fail silently** (SCHEMA-004). `run()` catches every error and logs a
   `warn`. And `CREATE UNIQUE INDEX IF NOT EXISTS` **fails if duplicates already
   exist** — so "guard missing → duplicates accumulate → bootstrap can never
   succeed again" is self-locking, and announces itself only as a warn line.

## 5. Production configuration

Driving the **real compiled `typeOrmFactory`** across an environment matrix:

| NODE_ENV | TYPEORM_SYNCHRONIZE | role | result | synchronize | migrationsRun |
|---|---|---|---|---|---|
| `production` | `true` | api | **THROWS** `❌ TypeORM synchronize is NOT allowed in production` | — | — |
| `production` | `true` | **worker** | **THROWS** — identical guard | — | — |
| `production` | `false` / unset | api | proceeds to migrations | `false` | `false` |
| `production` | `TRUE` / `1` | api | proceeds (`=== 'true'` is exact — fails closed) | `false` | `false` |
| `development` | `true` | api & worker | boots | `true` | `false` |
| `test` | `true` | api | boots | `true` | `false` |
| unset | `true` | api | boots | `true` | `false` |

Confirmed alongside:

- **Migrations remain enabled.** `migrationsRun: false` in every case is correct
  and not a defect: migrations are run explicitly by
  `runMigrationsWithAdvisoryLock` *before* the DataSource is constructed, behind
  a Postgres advisory lock, so TypeORM's own runner is deliberately unused.
- **No alternate DataSource enables synchronize.** All three others —
  `src/config/data-source.ts` (migration CLI), `run-migrations-with-lock.ts`
  (boot-time runner) and `src/seed/data-source.ts` — hardcode or default to
  `synchronize: false`. `scripts/verify-migrations.ts` likewise.
- **The worker does not diverge.** `worker.module.ts` calls the same
  `typeOrmFactory` with `poolRole: 'worker'`; only pool size and timeouts
  differ.
- **Test configuration does not leak into production.** The `NODE_ENV=test`
  branches affect only rate limiting and SQL logging.
- **Environment precedence is understood.** `ConfigModule.forRoot({ validate })`
  runs Joi, which restricts `NODE_ENV` to `development|production|test`, and
  `ConfigService.get` prefers the validated value over raw `process.env`. So the
  case-sensitivity weakness below is **not** reachable through a normal boot.

Two caveats, both filed:

- The TLS gate fires **before** the synchronize guard: with
  `NODE_ENV=production` and no `DB_SSL_CA`/`DB_SSL_CA_CERT`, the factory throws
  on certificate policy first. The synchronize guard is the second line of
  defence, not the first. (Both hold; the ordering only matters when reading a
  boot failure.)
- **`src/migrate.ts` runs no Joi validation at all** — it reads `process.env`
  directly by design. `databaseSslOptions` compares `NODE_ENV === 'production'`
  exactly, so `PRODUCTION`, `production ` or `prod` in a migration job silently
  disables certificate verification. It cannot enable synchronize
  (`data-source.ts` hardcodes it off), so this is a TLS finding, not a schema
  one (SCHEMA-007).

**Not covered by any test.** `typeorm.config.spec.ts` has 14 cases and none
assert the production guard (SCHEMA-008).

## 6. Migration drift across environments

The same 43-object check against every reachable database:

| database | migrations recorded | critical guards | verdict |
|---|---|---|---|
| `ziyarati_e2e` | 132 | **43 / 43** | **ENFORCED** |
| `ziyarati_perf_t2` | 75 | 33 / 43 | CRITICAL — 5 P0 absent, 1 definition mismatch |
| `ziyarati_perf` | **133** | 24 / 43 | CRITICAL — 4 P0 absent |
| `ziyarati` (dev) | 118 | 15 / 43 | CRITICAL — 7 P0 absent |
| `p02_audit` (control) | 133 | 15 / 43 | CRITICAL — 7 P0 absent |
| **production** | — | **NOT INSPECTED** | **UNKNOWN** |

Three things this table establishes:

1. **`ziyarati_e2e` is the reference.** Built from the migration chain by
   `test/setup-e2e-db.js`, it passes all 43 checks — which also validates the
   verification script itself: zero false positives on a correct schema.
2. **Dev is exactly a synchronize-damaged database** — 15/43, identical to the
   control. The attribution is unambiguous.
3. **`ziyarati_perf` records all 133 migrations and is still missing four P0
   guards.** That is the P0.1 signature — recorded as applied, not present —
   reproduced in a second database.

Flags applied (from the brief):

| flag | where |
|---|---|
| `MIGRATION_SAYS_APPLIED_BUT_OBJECT_MISSING` | dev, perf, perf_t2 — SCHEMA-009 |
| `MIGRATION_MISSING_BUT_OBJECT_EXISTS` | 10 FKs present in dev only — SCHEMA-005 |
| `DEFINITION_MISMATCH` | `UQ_customers_tenant_email` in perf_t2 — SCHEMA-010 |
| `SYNCHRONIZE_VULNERABLE` | 32 integrity objects — SCHEMA-001 |
| `BOOTSTRAP_DEPENDENCY` | 32 objects that survive only via a bootstrap — SCHEMA-004 |

### Load-test results are unaffected, and here is the limit of that claim

`ziyarati_perf` is missing 19 of 43 guards, and the massive-scale and P0.1
contention runs used it. Those results stand: they measured the appointment
booking path, and `appointments_no_overlap` was independently verified present
before and after every run. But **no load test against that database is evidence
about any other guard.**

## 7. Does PostgreSQL enforce each guard independently of application code?

The question the brief asks for every integrity guard. Answered by the
verification script, per database. On the reference schema (`ziyarati_e2e`):
**yes for all 43**, plus both extensions, the append-only trigger and its
function.

On every other local database: **no, for between 10 and 28 of them.**

For production: **unknown, and unknowable from here.** The one action this audit
asks for is:

```bash
psql "$DATABASE_URL" -f tests/load/reports/P0.2_PRODUCTION_VERIFICATION.sql
```

It reads only `pg_catalog` / `information_schema`, writes nothing to any user
table, and takes no locks beyond ordinary catalog access. It does create two
**session-local temporary views** to hold the expected values; they are
invisible to other connections and vanish on disconnect. There is no
INSERT/UPDATE/DELETE and no persistent DDL. (If a policy forbids even temp
objects on production, run it against a read replica.) It prints `PASS` /
`FAIL` / `MISMATCH` per object with the exact expected definition, a
per-severity summary, and a one-line overall verdict. It additionally checks the two extensions, the append-only
trigger, and every tenant-scoped table for a foreign key to `tenants`
(structurally, ignoring names, because TypeORM renames foreign keys).

Validated in both directions before shipping: `ENFORCED — all 43` on the clean
reference database, `CRITICAL — 7 P0 absent` on the synchronize-damaged control.

## 8. What this audit did not do

- **No repairs.** No object was created, dropped or altered outside the
  disposable `p02_audit` database. No migration history was rewritten. No
  application code was changed.
- **Production was not inspected.** Nothing here can tell you what production
  contains.
- **Performance indexes were not individually assessed.** 56 are lost on a
  synchronize boot; they are counted, not triaged, because losing one costs
  latency rather than correctness.
- **The 13 tenant tables without a tenant FK were not triaged** into
  "deliberate" versus "gap". Several are raw-SQL append-only tables whose
  docstrings say the design avoids entity mapping on purpose; whether the
  missing FK was intended is not recorded anywhere the audit could find.
- **`ziyarati_perf_t2`'s drift was not root-caused** beyond noting it has 75 of
  133 migrations.

## 9. Recommended remediation order (for a later phase — none performed)

1. **SCHEMA-004** — make integrity-guard bootstrap failures loud (`error` + a
   metric). Smallest change, and it is the only one with a *production* blind
   spot: today a missing guard in production reports itself as one `warn` line.
2. **Run the production verification.** One read-only command; it converts the
   single largest unknown into a fact.
3. **SCHEMA-008** — three unit tests pinning the production synchronize guard.
4. **SCHEMA-001 remediation 1** — set `TYPEORM_SYNCHRONIZE=false` and let
   migrations own every schema. This deletes SCHEMA-001, -002, -003 and half of
   -005 at once, and makes local databases valid rehearsals for production.
   Requires rebuilding the local databases (re-running recorded migrations
   repairs nothing — P0.1 DRIFT-002).
5. **SCHEMA-005 / -006** — decide the canonical foreign-key set, then migrate
   the adopted ones with orphan pre-checks that abort rather than delete.
6. **SCHEMA-007** — normalise `NODE_ENV` in `databaseSslOptions`, or validate in
   `migrate.ts`.
