# P0.1 — Appointment Integrity Remediation: `appointments_no_overlap`

**Date:** 2026-09-02
**Trigger:** MS-001 of `MASSIVE_SCALE_FINDINGS.md` — a 500-VU contention run put
**495 appointments into one doctor's single 15-minute slot**, every one of them
HTTP 201, while the `migrations` table reported the guard as applied.
**Status:** **RESOLVED in code and in every reachable database.**
**Production status:** **NOT VERIFIED — see §10. Nothing in this repository can
prove what production's schema contains; an operator must run the query.**

---

## 0. One-paragraph summary

The migration that creates `appointments_no_overlap` is **correct**. It was never
the problem. The constraint was created properly and then **destroyed
afterwards, by the application itself**: every boot with
`TYPEORM_SYNCHRONIZE=true` runs TypeORM's schema synchronizer, whose
`dropOldExclusions()` drops any EXCLUDE constraint it does not find in entity
metadata. The same flag also skips the migration chain, so the migration never
re-ran, its `migrations` row survived, and the database reported itself fully
migrated with the guarantee gone. This is now closed from both ends: the
`Appointment` entity **declares** the constraint (so the synchronizer recognises
it and never drops it — and creates it on databases built by synchronize), and a
new idempotent repair migration restores it on databases that already lost it.

## 1. Root cause

### 1.1 What it is

`src/config/typeorm.config.ts`:

```ts
const enableSync  = config.get<string>('TYPEORM_SYNCHRONIZE') === 'true';
const synchronize = !isProduction && enableSync;
...
if (!synchronize) {
  await runMigrationsWithAdvisoryLock(databaseUrl, ssl);
}
```

One flag does two damaging things at once:

1. **It skips the migration chain entirely.** Migrations never run, so a
   constraint that is missing can never be restored by booting.
2. **It enables the schema synchronizer**, which actively *removes* schema
   objects it cannot derive from entity metadata.

`node_modules/typeorm/schema-builder/RdbmsSchemaBuilder.js`:

```js
171:  await this.dropOldExclusions();
364:  async dropOldExclusions() {
372:      const oldExclusions = table.exclusions.filter((tableExclusion) => {
373:          return !metadata.exclusions.find(
374:              (exclusionMetadata) => exclusionMetadata.name === tableExclusion.name);
380:      await this.queryRunner.dropExclusionConstraints(table, oldExclusions);
```

The match is **by name**. `appointments_no_overlap` existed only in migration
SQL, was therefore absent from `metadata.exclusions`, and was therefore "old" on
every single boot.

### 1.2 Why it looked like a migration failure and was not

A failed migration cannot be the explanation, and the database says so.
`migrationsTransactionMode: 'each'` wraps each migration in its own transaction,
so had the `ALTER TABLE` failed, the `CREATE EXTENSION IF NOT EXISTS btree_gist`
on the line above it would have rolled back too, and no `migrations` row would
have been written.

What was actually observed in the dev database `ziyarati`:

| fact | value | what it proves |
|---|---|---|
| `migrations` row for `AppointmentNoOverlap1730001100000` | **present** (id 13) | the migration ran to completion and committed |
| `btree_gist` extension | **present** (1.8) | its *first* statement committed |
| `appointments_no_overlap` in `pg_constraint` | **absent** | its *second* statement's effect was removed later |

The only writer of `btree_gist` anywhere in this repository is that migration
(`grep -rn btree_gist src/ test/ scripts/` → one file). So the migration ran,
succeeded, and something dropped the constraint afterwards while leaving the
extension and the migration row alone. `down()` cannot be that something — it
deletes the `migrations` row.

### 1.3 Causes explicitly ruled out

| candidate cause | ruled out by |
|---|---|
| migration marked executed but DDL failed | `btree_gist` present + `migrationsTransactionMode: 'each'` (§1.2) |
| migration generated incorrectly | fresh DB → 132 migrations → constraint present, definition byte-identical (§3.2) |
| migration executed against another database | the `migrations` row and the missing constraint are in the *same* database |
| manual schema modification | reproduced from scratch with no human SQL (§3.3) |
| PostgreSQL extension/type dependency | `btree_gist` 1.8 present in every environment checked |
| deployment race | `runMigrationsWithAdvisoryLock` serialises on a Postgres advisory lock; and the drop is issued by a *single* boot |
| database restore / schema reset | reproduced on a database created minutes earlier |
| **`synchronize`** | **CONFIRMED — reproduced end to end, drop statement captured (§3.3)** |

argument, not proof.** It assumes production actually runs with
`NODE_ENV=production`, and it says nothing about what a past deployment,
restore, or manual operation did. **Run the §10 query. Do not infer.**

## 5. The correction

Two changes, and **both are required**. The migration alone would be undone by
the next dev boot; the decorator alone would not help a database that already
lost the constraint, because the original migration is recorded as applied and
will never re-run.

### 5.1 `src/migrations/1730088000000-AppointmentNoOverlapRepair.ts` (new)

Restores the constraint on an existing database. Properties, each demanded by
the brief:

- **Idempotent** — returns early if the constraint is already present.
  Verified against `ziyarati_perf`, which already had it: migration applied,
  constraint untouched, 60,015 rows unchanged.
- **Never deletes or edits appointment data.** If overlapping rows exist it
  **aborts**, naming every count, and changes nothing.
- **Fails loudly.** Counts are placed in the exception MESSAGE, not in DETAIL,
  because node-postgres surfaces only `error.message` through TypeORM — anything
  in DETAIL is invisible to `npm run migration:run`. (Found by running the abort
  through the CLI and seeing the detail vanish.)
- **Post-condition asserted** — a repair migration that silently did nothing is
  the exact failure this phase exists to eliminate.
- **`down()` is a deliberate no-op**, documented: reversing "the guard must
  exist" would re-open the hole on an operator's machine. The constraint remains
  owned by `AppointmentNoOverlap1730001100000`.

Abort behaviour, exercised against a 60,018-row clone with 3 injected overlaps:

```
[migrate] FAILED: Cannot install "appointments_no_overlap": 3 overlapping
appointment pair(s) already exist (appointments involved=6, staff=3, tenants=3,
branches=3). No rows were changed — resolve the conflicts, then re-run this
migration.
```

Exit code 1. Afterwards: **60,018 rows still present** (nothing deleted),
constraint not installed, migration **not** recorded — so it retries. After
cancelling one side of each pair, the same command applied cleanly and the
constraint installed. The full documented recovery loop works.

### 5.2 `@Exclusion` on the `Appointment` entity

```ts
@Exclusion(
  'appointments_no_overlap',
  `USING gist ("staffId" WITH =, tstzrange("start_at", "end_at", '[)') WITH &&) ` +
    `WHERE (status NOT IN ('CANCELLED','NO_SHOW') AND deleted_at IS NULL)`,
)
```

This is the actual root-cause fix. Three verified consequences:

1. **The synchronizer no longer drops it** — it matches by name, and the name is
   now in `metadata.exclusions`.
2. **It creates it where it never existed.** A database built *purely* by
   synchronize (153 tables, **no `migrations` table at all**) now gets the
   constraint, with a byte-identical definition. That closes the failure mode
   `SchedulingIntegrityService` was written to warn about.
3. **`btree_gist` comes along automatically** — `PostgresDriver` installs it
   when any entity declares an exclusion constraint (`PostgresDriver.js:406-409`),
   so a synchronize-built database is not left with an unsatisfiable operator
   class.

The claim in the old code comment — "TypeORM cannot express an EXCLUSION
constraint in entity metadata" — is **false**; `@Exclusion(name, expression)` has
existed all along, and `PostgresQueryRunner.createExclusionConstraintSql` emits
`ALTER TABLE … ADD CONSTRAINT "<name>" EXCLUDE <expression>`, which accommodates
both `USING gist (…)` and the partial `WHERE`. That incorrect belief is the
reason the constraint was left outside entity metadata, and is therefore the
proximate cause of the whole defect.

### 5.3 Proof both halves work

| step | result |
|---|---|
| drifted DB (`ziyarati_drift`, guard missing) → `migration:run` | `applied AppointmentNoOverlapRepair…`; constraint present, definition byte-identical |
| same DB → `migration:run` again | `no pending migrations — schema already current` |
| same DB → boot with `TYPEORM_SYNCHRONIZE=true` | **constraint still present**; `LOG [SchedulingIntegrityService] Double-booking guard verified` |
| **dev DB `ziyarati`** → ordinary developer boot, nothing else | **constraint created automatically**; guard verified |
| empty DB → synchronize-only boot (no migrations at all) | constraint created, byte-identical |
| fresh DB → full chain via the repo's own harness | `✓ ran 133 migrations from empty DB` |

### 5.4 `SchedulingIntegrityService` message corrected

Its diagnosis was wrong in a way that would have misdirected the next operator:
it blamed "this database was built with `TYPEORM_SYNCHRONIZE=true`" (a database
built that way has an *empty* migrations table — not what was observed) and
asserted TypeORM cannot express EXCLUDE. It now states the real cause, tells the
reader not to trust the migrations table, names the repair migration, and
explicitly says never to delete booking rows to force the constraint through.

The service remains **log-only and never fatal**, unchanged and deliberately so.

## 6. Application behaviour — all write paths

`mapTypeOrmError` (`src/common/errors/typeorm-error.mapper.ts:136`) maps
SQLSTATE **23P01** on this constraint to `ErrorCode.SLOT_ALREADY_BOOKED` → **HTTP
409**. It is reached from `error-normalizer.ts:47`, which is driven by the global
`AllExceptionsFilter`, so **every** path funnels through it rather than each
service handling it individually.

| path | method | reaches the constraint | observed |
|---|---|---|---|
| create | `AppointmentsService.create` → `manager.save` inside `dataSource.transaction` | yes | **409 `SLOT_ALREADY_BOOKED`**, 1,119 times server-side, 0× 5xx |
| reschedule | `AppointmentsService.reschedule` → `save(appointment)` inside a transaction, availability re-checked with `excludeAppointmentId` | yes — an UPDATE violates an exclusion constraint exactly as an INSERT does | 409 by the same mapper |
| update | `AppointmentsService.update` inside `dataSource.transaction` | yes | 409 by the same mapper |
| cancel | sets `status = CANCELLED` | n/a — the partial `WHERE` excludes cancelled rows, so cancelling **frees** the slot immediately | — |

**Measured, never 500:** across every P0.1 run the API log contains
**0 occurrences of `"statusCode":5`** and **0 pool-acquisition timeouts**, against
**2,238 log lines recording 1,119 exclusion-constraint violations**.

One nuance worth recording because it changes how the numbers read: of ~7,000
client-observed 409s, only **1,119 were genuine constraint arbitrations**. The
remaining **6,450 were `STAFF_NOT_AVAILABLE`** — once a winner has committed,
later attempts are rejected by the application's own availability check before
they ever reach the database. Both are correct 409s, but only the former
exercises the guard. A sequential double-booking attempt therefore proves
nothing about the constraint (verified: attempt 1 → 201, attempt 2 → 409
`STAFF_NOT_AVAILABLE`); **only concurrency does**.

### 7.2 The threshold breach is transport, not application — and it is proven, not asserted

At 500 VUs, 1,202 requests failed with `dial: i/o timeout` — a **TCP connect
that never completed**, so the request never reached the server. Evidence that
this is the lab and not the application:

- **The server was idle-ish throughout**: event-loop lag p99 **0.135 s**, pool
  `active` peak **6 of 10**, longest active statement **0.020 s**, **zero** pool
  acquisition timeouts, **zero** 5xx. A saturated server produces 5xx or slow
  responses, not failed TCP handshakes.
- **The generator was not CPU-bound either**: k6 container CPU peaked at 206% of
  a 16-vCPU host at 500 VUs.
- **Reproduced at the smallest load, as the brief requires — and it does not
  reproduce.** The identical scenario at **100 VUs**, same server, same pool,
  same slot, produced **0 timeouts**, *more* completed requests (2,427 vs 2,216

  concurrency, not with any server-side quantity.

This matches the Windows/Docker-NAT ephemeral-port limit already characterised in
`MASSIVE_SCALE_LOAD_TEST_REPORT.md` §18. **It does not affect the correctness
result**: a request that never reached the server cannot have created a booking,
and the database confirms exactly one row.

## 10. Production verification procedure

**`scripts/verify-appointment-guard.sql`** — strictly read-only. No DDL, no DML,
no locks beyond ordinary catalog reads. Safe on a live production database.

```bash
psql "$DATABASE_URL" -f scripts/verify-appointment-guard.sql
```

It reports database name, constraint name, full definition, validated flag,
`btree_gist` version, the migration rows, the five conflicting-data counts, and a
one-line verdict. Both verdicts were exercised against real databases:

```
PROTECTED — appointments_no_overlap is installed and no overlapping appointments exist.

UNPROTECTED — appointments_no_overlap is NOT installed. Concurrent bookings for the
same staff and window can BOTH succeed (HTTP 201 for every one of them).
Run: npm run migration:run
```

**If the verdict is UNPROTECTED**, in order:

1. Run the query again on a read replica or with `count(*)` on `appointments` to
   size the table — the fix takes a lock proportional to it.
2. Schedule a maintenance window. **`ADD CONSTRAINT … EXCLUDE` takes an ACCESS
   EXCLUSIVE lock and builds a GiST index over every live row. PostgreSQL has no
   `CONCURRENTLY` and no `NOT VALID` form for exclusion constraints, so this
   cannot be made online. Bookings block for the duration.**
   **Measured: 15.16 s for 900,000 appointments** (`ziyarati_perf_t2`, drop and
   rebuild timed with `\timing`). Scale from your own row count.
3. Consider `SET lock_timeout = '5s'` first, so the `ALTER` fails fast rather
   than queueing behind a long-running read and blocking everything behind it.
4. `npm run migration:run`. If it aborts, it will name how many overlapping
   pairs exist and how many appointments, staff, tenants and branches are
   involved, and will have changed nothing. **Resolve those bookings as a
   business decision — cancel or reschedule one side of each pair. Never delete
   appointment rows to force the constraint through.**
5. Re-run the verification query. Expect `PROTECTED`.
