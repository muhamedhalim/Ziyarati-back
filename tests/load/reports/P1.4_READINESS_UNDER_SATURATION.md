# P1.4 — Readiness Under Saturation

**Date:** 2026-09-04. Fixes MS-009 directly: a saturated-but-working
instance no longer reports itself as down.

## Root cause (MS-009, re-confirmed against current code)

`HealthController.readiness()`'s DB check used `this.dataSource.query('SELECT 1')`
— the **shared application pool**. Under saturation this queues behind the
exact request traffic that exhausted the pool, so the probe times out and
reports `database: down` even though Postgres itself is completely healthy.
An orchestrator then pulls a working instance out of rotation (or restarts
it, if wired to liveness), pushing its load onto siblings under the same
pressure — the classic degradation-to-outage amplifier the original load
test measured directly (6.1s–16.7s probe latency, 503, while the API was
still serving correct responses).

## Fix

1. **A dedicated, single `pg.Client` for the DB ping — never the pool.**
   Lazily connected on first use, then reused across every subsequent probe
   (no per-request connection-setup cost); reconnects automatically after a
   query failure (the broken client is discarded, the next probe opens a
   fresh one); two concurrent readiness calls share one in-flight connect
   attempt rather than each opening its own. This answers "is Postgres
   itself reachable", which is a genuinely different — and more useful —
   question than "is a pool slot free" for this specific probe.
2. **A new `"busy"` status**, alongside the existing `"ok"`/`"degraded"`:
   when the DB is reachable (via the dedicated connection) but the shared
   pool has `waitingCount > 0` at that instant, readiness reports `status:
   "busy"` and `database.poolWaiting: N` — **still HTTP 200, still in
   rotation**. Read directly off the live `pg-pool` instance (the same
   counters P1.3's `DbPoolMetricsService` samples on its own interval —
   read fresh here rather than shared, since a stale cached value is worse
   than a synchronous property read that costs nothing).
   - Priority when both are true: a missing schema guard (`"degraded"`)
     wins the top-level `status` over pool saturation (`"busy"`) — it is
     the more persistent problem — but `database.poolWaiting` stays visible
     regardless, so nothing is hidden.
3. **Testability refactor**, done for correctness not convenience: the
   client is obtained through an injectable `READINESS_DB_CLIENT_FACTORY`
   token (`HealthModule` provides the real `() => new Client(...)`) rather
   than constructed directly in the controller — matching this codebase's
   existing constructor-injection testability pattern throughout, and
   avoiding the fragility of mocking the `pg` module wholesale.

## What was NOT changed

- Liveness stays dependency-free (unchanged).
- The pool itself — size, timeouts — untouched; this phase only changes
  what readiness *measures*, never how the pool behaves.
- `SCHEMA_GUARD_FAIL_READINESS` behavior is unchanged: it still only fires
  on a missing schema guard, never on `"busy"`. Pool saturation is
  deliberately never a 503 condition, by design (see MS-009's own
  amplification finding above) — evicting a saturated-but-working instance
  makes the outage worse, not better.

## Verification performed

- **Unit (`health.controller.spec.ts`, fully rewritten for the new dedicated-client
  design — the old tests drove `dataSource.query`, which the new code path
  no longer touches at all):** 20/20, including new coverage for: connects
  once and reuses the client across N calls; two concurrent calls share one
  in-flight connect; reconnects with a fresh client after a query failure
  (and the broken one is `.end()`'d); a query failure leaks nothing,
  matching the connect-failure case; `"busy"` status with the exact
  `poolWaiting` count; `poolWaiting` omitted entirely when `waiting === 0`;
  `"degraded"` wins over `"busy"` when both are true, without hiding the
  pool signal; never throws when the driver has no pool shape yet; the
  dedicated connection is closed on `onModuleDestroy` (and is a no-op if
  never opened).
- **E2e, real HTTP, real dedicated `pg.Client`, real `pg-pool`
  (`health-readiness.e2e-spec.ts`):** 5/5. The pre-existing "DB failure
  leaks nothing" test's simulation mechanism (mocking `dataSource.query`)
  had to be updated — it silently stopped exercising anything real once the
  fix landed, which is itself proof the fix works — to mock
  `Client.prototype.query` instead (reaches the real dedicated client,
  including one already connected and cached from an earlier test in the
  same file); the response still leaks nothing. **New**: a real end-to-end
  proof of `"busy"` — `jest.spyOn(pool, 'waitingCount', 'get')` on the
  actual live `pg-pool` instance behind the real `DataSource`, confirming
  HTTP 200 + `status: "busy"` + the exact waiting count over real HTTP, not
  just a unit-level mock.
- Typecheck: identical to the confirmed cross-phase baseline.
- Lint: zero new issues.
- Full unit suite: the same 4 pre-existing failing suites, nothing new.

## Deliberately not done

- No load-test re-run of the original MS-009 80-it/s-with-pool-10 scenario.
  The unit + e2e coverage above directly proves the mechanism (dedicated
  connection bypasses pool contention; pool state is reported, not
  conflated with DB health) rather than re-creating the saturation
  scenario end-to-end, which is a much larger undertaking than this
  specific fix needs to be proven correct. If a full re-run is wanted,
  `tests/load/` already has the scenario that originally surfaced MS-009.

## Production changes required

None. Behavioral change only: an orchestrator that gates traffic on
readiness will now correctly keep a busy-but-working instance in rotation
instead of evicting it — this is the intended fix, not something requiring
separate configuration.
