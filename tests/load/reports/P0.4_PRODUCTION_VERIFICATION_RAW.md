## 2. STEP 3 — proof the verification script is read-only

Four independent checks. Each would catch something the others could miss.

### 2a. Static statement scan

Comments, single-quoted literals and dollar-quoted bodies stripped; every
remaining statement classified **by its leading verb**, not by "does the text
contain DELETE" — matching on substrings produces false positives against
`BEFORE UPDATE OR DELETE ON transactions` inside a trigger body, which is how
the equivalent P0.3 check first failed.

```
file:                 tests/load/reports/P0.3_PRODUCTION_VERIFICATION.sql
SQL statements:       14
  read-only:          9
  CREATE TEMP ...:    5
  FLAGGED:            0
psql meta-commands:   27  (0 outside the safe set: \pset \echo \set \timing \x \a \t \f \C \encoding)

TEMP objects created (session-local, dropped at disconnect):
  p03_expected  p03_actual  p03_shape  p03_verdict  p03_conflict_checks
```

No `\copy`, `\i`, `\o` or `\!` — the four meta-commands that could reach
outside the session.

### 2b. The dynamic SQL a statement scan cannot see

§5b runs `EXECUTE r.check_sql` on 43 strings held in a TEMP VIEW. A scanner
that classifies by leading verb sees one harmless `DO` block and stops. Each of
the 43 was extracted **by position** (4th element of each `VALUES` tuple) and
tested individually:

```
single-quoted literals in the view: 172
check_sql statements executed:      43
guards in the contract fixture:     43
statements failing the read-only test: 0
```

Each must start with `SELECT`, contain no `;` (so a second statement cannot be
chained), no comment, no dollar-quote, and no mutating or side-effecting
keyword — with **string literals removed first**, because
`tenant_entitlement_ledger` filters on `(direction)::text = 'grant'::text` and
`'grant'` as a column value is not the `GRANT` statement.

**The checker was verified to fail.** A copy of the script with
`DELETE FROM users; ` prepended to one `check_sql`:

```
FAIL  DELETE FROM users; SELECT count(*) FROM users WHERE ((email IS NULL) ...
      does not start with SELECT; contains ";" — a second statement could be
      chained; contains mutating/side-effecting keyword: DELETE
statements failing the read-only test: 1
```

The first version of this checker **missed that injection** — it selected
candidates by "starts with SELECT", so the tampered row fell out of the sample
instead of failing it. Extraction was changed to be positional. A test that
cannot fail proves nothing.

### 2c. Executed as a role that cannot write

A role with `pg_read_all_data` and nothing else — no superuser, no createdb, no
createrole, no bypassrls. Control, confirming the role really is powerless:

```
CREATE TABLE p04_should_fail (x int);          ERROR:  permission denied for schema public
INSERT INTO users (id) VALUES (...);           ERROR:  permission denied for table users
DROP INDEX IF EXISTS uq_message_wa_id;         ERROR:  must be owner of index uq_message_wa_id
```

Then the script itself, as that role, against two local databases:

```
ziyarati_e2e   exit=0   0 errors   P03_STATUS=ENFORCED
ziyarati (dev) exit=0   0 errors   P03_STATUS=CRITICAL
```

It completed. Every statement it ran was therefore a read.

> A stricter form — `default_transaction_read_only=on` — was tried first and
> **cannot** run this script: PostgreSQL 18 refuses `CREATE TEMP VIEW` in a
> read-only transaction (`ERROR: cannot execute CREATE VIEW in a read-only
> transaction`). Recorded because it is the obvious next idea for anyone
> repeating this, and it does not work.

### 2d. Before/after fingerprints

Three measures per database: a catalog fingerprint (relations, indexes,
constraints, triggers, columns), an exact row count of every table, and
PostgreSQL's own tuple counters — the third catches a write that was rolled
back, which the first two would both miss.

```
ziyarati_e2e   BEFORE  catalog_md5=f2b8a95b9f01e7b02d6df3833af6ab51
                       rowcount_md5=9cb29ad6321a776d94fd3125626d9147
                       tup_ins=369 tup_upd=28 tup_del=360
               AFTER   catalog_md5=f2b8a95b9f01e7b02d6df3833af6ab51   IDENTICAL
                       rowcount_md5=9cb29ad6321a776d94fd3125626d9147   IDENTICAL
                       tup_ins=462 tup_upd=33 tup_del=451              +93 / +5 / +91

ziyarati (dev) BEFORE  catalog_md5=6cf52189bb8220e190812cda478c5a6a
                       rowcount_md5=b6b8f9bc8e1472356cab8aa8dd1325aa
                       tup_ins=894 tup_upd=61 tup_del=914
               AFTER   catalog_md5=6cf52189bb8220e190812cda478c5a6a    IDENTICAL
                       rowcount_md5=b6b8f9bc8e1472356cab8aa8dd1325aa    IDENTICAL
                       tup_ins=987 tup_upd=66 tup_del=1005             +93 / +5 / +91
```

**The tuple counters moved, and the reason was measured rather than assumed.**
Creating five TEMP views in one session and disconnecting, with no other
activity, costs:

```
tup_inserted +63   tup_updated +5   tup_deleted +61
```

That is `pg_catalog` bookkeeping — the temp schema and the temp views' rows in
`pg_class`, `pg_attribute`, `pg_type`, `pg_rewrite`, `pg_depend` — inserted at
creation and removed when the session ends. The snapshot script itself was
checked separately and moves the counters by **0**.

So: **no application row was inserted, updated or deleted; no catalog object
changed.** An operator watching `pg_stat_database` on production will see a
small blip of this shape and should not read it as a write.
