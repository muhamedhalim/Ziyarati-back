## Class A — safe to add now (10 tables)

**Why "safe":** zero orphan rows on both `ziyarati` (6+ years of campaign
churn — the more adversarial of the two references) and `ziyarati_e2e` (the
migration-built reference matching how production is built). Two-step
migration (`NOT VALID` then `VALIDATE`) means the first step is metadata-only
and cannot fail on data even if this phase's read of "zero orphans" is
somehow stale by the time it runs against a different target; the second
step is what actually proves clean data, and fails cleanly (no partial
state, no data change) if it isn't.

**`ON DELETE`: `NO ACTION`** (Postgres's default, so simply omitted) for
every one of the 10 — matching the dominant existing convention in this
schema: measured via `pg_constraint.confdeltype` across all 113 pre-existing
foreign keys to `tenants`, **88 use `NO ACTION`, 25 use `CASCADE`, none use
`SET NULL` or `RESTRICT`**. None of these ten tables is a pure derived
cache that should vanish with its tenant, and — the more important fact —
**this codebase has no tenant-delete code path at all today** (grepped:
`TenantsService` has no `remove`/`delete`/`softDelete` method; `Tenant.
deleted_at` is written by nothing). Choosing cascade behaviour for a future
tenant-delete feature is that feature's decision, not a side effect of this
migration.

**FK names:** computed with TypeORM's own `DefaultNamingStrategy.
foreignKeyName()`, verified by reproducing — byte for byte — the four names
TypeORM's synchronizer already assigned on `ziyarati` for the four tables
whose entities already declare `@ManyToOne(() => Tenant)`
(`ai_execution_metrics`, `ai_memories`, `workflows`, `workflow_runs`). The
other six use the same function for the same reason: every one of the other
113 foreign keys in this schema is named this way; none by hand.

**Two entities converged, not just migrated (`admin_notifications`,
`email_logs`):** both previously declared `tenant_id` as a plain `@Column`.
Adding the FK via migration alone, without an entity relation, would
recreate the exact class of defect P0.1/P0.2 exist to close — a
`TYPEORM_SYNCHRONIZE=true` boot drops any foreign key entity metadata does
not describe, the same way it dropped `appointments_no_overlap`. Both
entities now declare `@ManyToOne(() => Tenant) @JoinColumn({name:
'tenant_id'})`, column name and nullability unchanged. The 3 ORM-level write
sites this touched (`admin-notification.service.ts:1`,
`email-delivery.service.ts:2`) were updated from `tenant_id: string` to
`tenant: {id} as Tenant` — the same pattern `ai-metrics.service.ts` already
uses for `AiExecutionMetric`. Every *read* site for both tables uses raw SQL
(unaffected by this — the physical column is unchanged).

**Supporting index:** only `admin_notifications` had none on its tenant
column (the other 9 already do — see the forensic table). Added in the same
migration, before the constraint.

## Class B — blocked by an existing orphan (1 table)

### `tenant_counters` — 1 orphaned row out of 1, on `ziyarati`

The table's **only** row on dev references a `tenant_id` with no matching
row in `tenants`. `ziyarati_e2e` has zero rows in this table at all, so this
is not reproducible there. **Not repaired, not investigated further, and no
survivor chosen** — per RULE 9 (carried from P0.3): a single orphaned row is
still someone else's data question, not a default to apply unilaterally.

**What would need to happen before an FK could be added:** a decision on
this one row — delete it (it is dead weight: the invoice-numbering counter
for a tenant that no longer exists in `tenants`) or leave the table without
an FK. Given the row count is exactly 1 and the table's only consumer
(`invoice.service.ts`) upserts by `(tenant_id, name)`, this is very likely
low-risk to resolve — but "very likely low-risk" is exactly the kind of
judgement this phase does not get to make unilaterally.

**Production status: unknown** — not scanned by this phase. See *Handover*.

## Class D — requires a type migration first (2 tables)

### `subscription_invoices.tenant_id`, `subscription_usage.tenant_id` — `character varying`, not `uuid`

Confirmed again this phase (P03-006's finding still holds): a foreign key on
either column is structurally impossible without `ALTER COLUMN ... TYPE
uuid` first — an **ACCESS EXCLUSIVE, full-table-rewrite** operation, not
reversible in place, needing its own backup and window. **Not attempted
here** and not batched with anything else, per instruction.

**New this phase — the values themselves are clean:** `0` non-uuid-shaped
values in either column, on `ziyarati` (207 + 1 rows) or `ziyarati_e2e` (0
rows). So the eventual type change is not blocked by malformed data, only by
its own operational cost. This does not extend to production, which was not
scanned.

**New, real finding this phase surfaced — `subscription_usage` has a SEPARATE
orphan problem, worse than the type issue:**

> On `ziyarati_e2e` — the migration-built reference, the one that should
> look like a clean, freshly-migrated production — **all 20 of 20
> `subscription_usage` rows reference a `tenant_id` with no matching row in
> `tenants`.** `ziyarati` (dev) shows 0 orphans out of 207 rows, the
> opposite pattern.

This is not the already-known 189-row conflict (`UQ_subscription_usage_
tenant_period_unsubscribed`, P03-001, dev-only, billing-decision-blocked,
untouched here) — this is a **referential** orphan (points at a tenant that
no longer exists), found by this phase, on a **different** database, for a
**different reason**. The most likely explanation: e2e is a long-lived,
shared database across many test files (not reset between files), and some
test's tenant-cleanup path deletes `tenants` rows directly (there is no
application-level tenant-delete path, so this can only be test-fixture SQL)
without cascading to `subscription_usage`. **Not root-caused further this
phase** — read-only forensics, not a debugging pass — logged as **FU-013**
(`FOLLOWUP_FINDINGS.md`) for whoever next touches e2e test fixtures.

**Consequence for planning:** even after a hypothetical future type
migration, `subscription_usage` would need its **own** orphan-cleanup pass
(on top of the type change) before an FK could validate — it cannot be
treated as "just like the other varchar table" once the type problem is
solved. `subscription_invoices` has no equivalent finding (0 orphans on
both).

## Class E — intentionally no FK (2 tables)

### `verification_audit_logs` — by design

`VerificationAuditLog.ts`'s own docstring: *"Uses plain scalar columns (no
FK relations) on purpose: the trail must survive deletion of the tenant or
document it references, and must never be mutated."* Reinforced structurally
this phase: the column is `NOT NULL`, so even `ON DELETE SET NULL` is not an
option — the only FK actions available would be `CASCADE` (deletes audit
history with its tenant — exactly what an audit trail must not do) or
`RESTRICT`/`NO ACTION` (blocks a hypothetical future tenant deletion
entirely, which is also not this table's call to make). **No migration
written, and none should be, for this table.**

The 6 orphaned rows measured on dev this phase are **consistent with, not
contrary to, that design** — an audit trail is expected to retain rows
whose tenant later became invalid. Their actual origin (there is no
tenant-delete code path in this app) is most likely the same class of
dev-database churn across P0.1–P0.4's own repeated scratch-database work,
not a production-relevant mechanism. Not investigated further — logged
alongside FU-013 as a low-priority "worth a root-cause pass someday", not a
blocker.

### `ai_memory_embeddings` — redundant with `ai_memories`'s new FK

A pgvector sidecar TypeORM never manages (no entity, by design — see
`AiMemory.ts`'s own docstring on why: keeps the `vector` column safe from
`synchronize`). Its `tenant_id` is reachable through `ai_memories(id)`,
which already has its own `ON DELETE CASCADE` foreign key to
`ai_memory_embeddings.memory_id`. Adding a **second**, direct tenant FK here
would enforce nothing an application already can't violate (a memory embed
row cannot exist without its parent memory, which is itself tenant-scoped)
and would be one more constraint TypeORM's synchronizer has no metadata for
— on a table already deliberately kept outside synchronize's reach. **No
migration written.**

## Verification performed (all read-only against disposable databases — never `ziyarati`, `ziyarati_e2e`, or production)

1. **Forensic scan** — `P0.7_TENANT_FK_VERIFICATION.sql` run against
   `ziyarati` and `ziyarati_e2e` (read-only; every statement is `SELECT`;
   statically confirmed — grepped for every mutating keyword, zero matches
   outside comments). Raw output: `tests/load/reports/p07/dev-verification.txt`,
   `tests/load/reports/p07/e2e-verification.txt`.
2. **Full chain from empty** — a disposable database (`p07_virgin`,
   dropped after) ran all 135 migrations (133 existing + these 2) via
   `node dist/src/migrate.js run`. **Exit 0.** All 10 FKs present, all 10
   `convalidated = true`.
3. **Synchronize-boot metadata check** — a second disposable database
   (`p07_sync`, dropped after) booted the real compiled app with
   `TYPEORM_SYNCHRONIZE=true`. **`API_BOOT_OK`, exit 0.** No
   `EntityMetadataValidator` error (the exact risk of declaring a relation
   and a plain column on the same physical column at once — checked for
   specifically, given `admin_notifications`/`email_logs` changed shape).
   Synchronize independently built `admin_notifications`/`email_logs`'s FKs
   under the **exact same names** this phase hand-computed for the
   migration — cross-confirms the naming-strategy computation two different
   ways.
4. **Idempotency + validate against real drifted data** — cloned `ziyarati`
   byte-for-byte into a disposable database (`p07_devclone`, dropped after,
   via `pg_dump`/`pg_restore`) and ran the two migrations' exact SQL against
   it. Confirmed: the 4 already-present FKs (drift artifacts from
   `ziyarati`'s own synchronize history) were correctly **skipped**
   (`NOTICE`, not recreated, no name collision); the other 6 were freshly
   added; **all 10 validated successfully** against dev's real,
   already-measured-clean data.
   - *(Running the FULL migration chain incrementally against this clone,
     rather than the two new migrations' extracted SQL directly, hit the
     pre-existing, already-documented P03-004 defect —
     `PatientActionLinks1730063000000` — `relation "patient_action_links"
     already exists` — unrelated to this phase's migrations and already on
     record as "rebuild from empty is the only path" for converting a
     synchronize-built database to migrations-first. Worked around by
     extracting and running the two new migrations' own SQL directly,
     which is what this step actually needed to prove.)*
5. **Regression tests** — `email-delivery.service.spec.ts`,
   `email-log.controller.spec.ts`: 12/12 pass. Full `tsc --noEmit`:
   byte-identical to pre-phase baseline (zero new errors). Full lint sweep:
   0 errors on every touched/created file.

All four disposable databases (`p07_virgin`, `p07_sync`, `p07_devclone`,
plus the `pg_dump` file) were dropped/deleted after use. `ziyarati`,
`ziyarati_e2e` and production were never written to by this phase.

`P0.3_PRODUCTION_VERIFICATION.sql`. §2 gives orphan counts for all 15
