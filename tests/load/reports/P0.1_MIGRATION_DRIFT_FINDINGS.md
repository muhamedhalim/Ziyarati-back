# P0.1 — Migration drift findings

**Date:** 2026-09-02
**Scope:** why a migration recorded as applied was not actually present in the
database, and what else that mechanism can silently remove.

Findings DRIFT-001…003 are **fixed** (see
`P0.1_APPOINTMENT_INTEGRITY_REPORT.md`). DRIFT-004…008 are **logged, not
fixed** — they are outside P0.1's stated scope.

The governing lesson: **the `migrations` table is not evidence.** In this
codebase a migration row proves only that the migration *once ran*. It says
nothing about whether its effects still exist, because a later boot can remove
them without touching the row. Every schema assertion in this repository that
reads `migrations` instead of `pg_catalog` inherits that flaw.

---

## DRIFT-001 — `synchronize` silently drops the double-booking guard from a correctly-migrated database — **FIXED**

**Severity:** **Critical** (silent data-integrity loss; no error, no log, no
failing test, no client-visible symptom)
**Status:** Fixed — entity now declares the constraint; repair migration added.
**Affected files:** `src/config/typeorm.config.ts`,
`src/entities/Calendar&Appointments/Appointment.ts`,
`src/migrations/1730001100000-AppointmentNoOverlap.ts`,
`node_modules/typeorm/schema-builder/RdbmsSchemaBuilder.js:364`

**Evidence.** With `TYPEORM_SYNCHRONIZE=true`, `typeOrmFactory` both **skips the
migration chain** (`if (!synchronize) { await runMigrationsWithAdvisoryLock(…) }`)
and **enables the schema synchronizer**, whose `dropOldExclusions()` drops every
EXCLUDE constraint whose *name* is absent from entity metadata. Captured from a
real boot of `dist/src/main` against a freshly-migrated database:

```
[Nest] WARN [TypeORM] ⚠️ TypeORM synchronize ENABLED (DEV ONLY)
query: ALTER TABLE "appointments" DROP CONSTRAINT "appointments_no_overlap"
query: COMMIT
```

Before that boot: constraint present, definition byte-identical to the
migration's. After: absent, while the `migrations` row and the `btree_gist`
extension both survived — the exact signature observed in the dev database,
reproduced from an empty database in minutes.

Consequence, measured in Phase 2.2: 500 VUs on one 15-minute slot produced
**495 appointments and 122,265 overlapping pairs, every request HTTP 201**.

**Fix applied.** `@Exclusion('appointments_no_overlap', …)` on the entity — the
synchronizer matches by name, so it is no longer "old" and is additionally
*created* on synchronize-built databases — plus
`AppointmentNoOverlapRepair1730088000000` to restore databases that already lost
it, since the original migration is recorded and will never re-run.

## DRIFT-002 — A recorded migration can never repair its own effect — **FIXED (for this constraint)**

**Severity:** High (structural; applies to every migration in the repository)
**Status:** Fixed for `appointments_no_overlap` only, by adding a *new*
migration. The general problem remains.
**Affected files:** all of `src/migrations/`, `src/migrate.ts`

**Evidence.** Once `AppointmentNoOverlap1730001100000` is in the `migrations`
table, `migration:run` reports `no pending migrations — schema already current`
no matter what the schema actually contains. There is no reconcile step, no
checksum, and no post-condition verification against `pg_catalog`. The only
mechanism that can repair a drifted object is a brand-new migration — which
requires a human to first *notice* the drift.

**Recommended general fix:** a startup or CI reconciliation step that asserts a
small set of *critical schema invariants* against `pg_catalog` (exclusion
constraints, partial unique indexes, triggers — anything TypeORM cannot derive)
and fails the deploy, rather than trusting the migrations table.
`SchedulingIntegrityService` is the one-object prototype of exactly this idea;
it should be generalised into a list.

## DRIFT-003 — `SchedulingIntegrityService` misdiagnosed the cause it existed to detect — **FIXED**

**Severity:** Medium (correct detection, wrong remedy — would misdirect an operator)
**Status:** Fixed (message and docstring corrected; behaviour unchanged).
**Affected files:** `src/modules/scheduling/scheduling-integrity.service.ts`

**Evidence.** The service detected the missing guard correctly and had been
logging it at every boot — including throughout the entire P0 campaign, whose
contention arm consequently never exercised the constraint it claimed to prove.
But its stated cause was wrong in two ways:

1. *"this database was built with `TYPEORM_SYNCHRONIZE=true`, which skips the
   migration chain"* — a database built that way has an **empty** migrations
   table. The affected databases had 118 and 132 rows. They were built by
   migrations and **degraded afterwards**.
2. *"TypeORM cannot express EXCLUDE in entity metadata"* — **false**.
   `@Exclusion(name, expression)` exists, and
   `PostgresQueryRunner.createExclusionConstraintSql` emits
   `ALTER TABLE … ADD CONSTRAINT "<name>" EXCLUDE <expression>`, which supports
   both `USING gist (…)` and the partial `WHERE`.

**This second belief is the proximate cause of the entire defect.** It is why the
constraint was left outside entity metadata, which is precisely what made the
synchronizer treat it as droppable.

## DRIFT-004 — Every `synchronize` boot drops and rebuilds 20 further raw-SQL objects — **logged, not fixed**

**Severity:** Medium (correctness-neutral *today*, by accident rather than design)
**Affected files:** `src/config/typeorm.config.ts`, the module bootstraps that
issue `CREATE INDEX IF NOT EXISTS`

**Evidence.** The same synchronize transaction that dropped the exclusion
constraint also dropped **20 indexes**, nine of them uniqueness guards:

```
uq_payments_appointment_pending   uq_txn_webhook_event   uq_refund_idem
uq_refund_gateway_id              uq_message_wa_id       uq_message_status
uq_dashboard_metric               UQ_billing_upgrade_requests_active_target
UQ_tenant_usage_limit_overrides_active
```
plus 11 performance indexes (`idx_conversations_tenant_lastmsg`,
`idx_customers_tenant_created`, `idx_appointment_services_appt`,
`idx_payments_settlement_claim`, `idx_payments_revenue`,
`idx_ai_messages_tenant_created`, `idx_customer_reviews_tenant_created`,
`idx_analytics_events_tenant_created`, `idx_analytics_events_created`,
`idx_txn_payment`, `idx_refund_payment_status`).

**All 20 are re-created later in the same boot** by module bootstraps running
`CREATE INDEX IF NOT EXISTS`. Final state of the repro database: 20 present, 1
missing (the exclusion constraint, which has no such bootstrap). So today this
is churn, not loss.

**Why it is still a finding:** these guards survive by a coincidence of two
unrelated mechanisms, not by design. Any future index added in raw SQL *without*
a matching self-healing bootstrap becomes the next
`appointments_no_overlap` — silently dropped, migration row intact. Several of
these protect idempotency (`uq_refund_idem`, `uq_txn_webhook_event`,
`uq_message_wa_id`); losing one would produce duplicate refunds or
double-processed webhooks rather than an error.

**Recommended fix:** extend the DRIFT-002 invariant list to cover these names,
so their absence fails loudly instead of depending on a bootstrap ordering.

## DRIFT-005 — The dev database is 14 migrations behind and cannot catch up by booting — **logged, not fixed**

**Severity:** Low (dev only, but it makes dev an unreliable place to reproduce
schema-dependent bugs)
**Affected files:** `.env` (`TYPEORM_SYNCHRONIZE=true`), `src/config/typeorm.config.ts`

**Evidence.** `ziyarati` has **118** migration rows; the chain now has **133**.
Because `synchronize` skips migrations entirely, booting will never close that
gap — the schema is instead whatever TypeORM derives from entities plus whatever
the bootstraps create. Two objects absent from dev but present in a
migration-built database confirm it: `UQ_billing_upgrade_requests_active_target`
and `UQ_tenant_usage_limit_overrides_active`.

Deliberately **not** repaired during P0.1: running 14 unrelated pending
migrations against the developer's database is well outside this phase's scope.
The double-booking guard itself is now present in dev (it self-healed from the
entity declaration on the next ordinary boot).

**Recommended fix:** either set `TYPEORM_SYNCHRONIZE=false` in the tracked `.env`
and let migrations own the dev schema — the same model production and the e2e
harness already use — or add an explicit `npm run db:sync-dev` step. The current
default makes dev structurally different from every other environment.

## DRIFT-006 — `scripts/verify-migrations.ts` reverts by fixed depth and is already misaligned — **logged, not fixed**

**Severity:** Medium (a schema-safety harness that reports failures unrelated to
what changed will be ignored, which is worse than not having it)
**Affected files:** `scripts/verify-migrations.ts`

**Evidence.** The script's own comments admit the design: *"the fixed-depth
`undoLastMigration()` cascades further down this script (each of which assumes a
specific named migration is the tail)"*. Its first cascade is commented
`// ReadPathIndexes down`, but `BranchManagerRole1730087000000` already sits
after `ReadPathIndexes1730086000000`, so that pop reverts the wrong migration —
**before** any P0.1 change.

Measured, with the P0.1 migration temporarily removed to get a clean baseline:

| | ✓ | ✗ |
|---|---|---|
| baseline (no P0.1 migration) | 6, then abort | 4 (`ReadPathIndexes down…`, `M2 down…` ×3) |
| with P0.1 migration | 44 | 18 |

The same checks fail in both. Adding *any* migration at the tail shifts every
cascade and changes which assertions fail; it also happens to let the run
progress further, which is why the counts differ. The forward path is healthy in
both: `✓ ran 132 migrations from empty DB` → `✓ ran 133 migrations from empty DB`.

**Recommended fix:** revert by *name* (look up the target migration and undo down
to it) instead of by count, or snapshot and restore the applied set around each
block.

## DRIFT-007 — A stray file in `src/` is a serialised shell command — **logged, not fixed**

**Severity:** Low (clutter; not loaded, because the migrations glob is
`src/migrations/*.ts` and this sits in `src/`)
**Affected files:** `src/migrations"\nls D:projectsZiyarati-fullZiyarati-backsrcmigrations"`

**Evidence.** `ls -la src/` lists a 3,026-byte regular file whose **name contains
a literal newline** and a fragment of a mangled shell command. Its contents are a
complete, valid copy of `ReadPathIndexes1730086000000` — the residue of a
redirect that lost its quoting. The real migration exists correctly at
`src/migrations/1730086000000-ReadPathIndexes.ts`, so nothing is missing.

**Recommended fix:** delete it. Not deleted here only because P0.1's scope is the
appointment constraint and the file is inert; a filename containing a newline
also needs care to remove safely.

## DRIFT-008 — The load harness overwrites its own per-run summary — **logged, not fixed**

**Severity:** Low (evidence loss; it cost this investigation one run's numbers)
**Affected files:** `tests/load/scenarios/appointments-write.js` (`handleSummary`)

**Evidence.** `handleSummary` writes to the fixed path
`/reports/appointments-write.json`, so each run overwrites the previous one's
summary. The 500-VU contention run's `timeouts: 1202` was captured only because
it was read before the next run started; the repeat run's equivalent figure is
**not retained** and is reported as such in
`P0.1_APPOINTMENT_INTEGRITY_REPORT.md` §7.1. Other scenarios in this directory
already name their output by `RUN_TAG`.

**Recommended fix:** name the file by `RUN_TAG` as the sweep and ladder scenarios
do.
