# P1.5 — Reminder/Webhook Loss (MS-007)

**Date:** 2026-09-04. Fixes MS-007: reminder scheduling for a newly-created
appointment no longer competes for a pool connection after the booking
transaction has already committed.

## Root cause (MS-007, re-confirmed against current code)

`ReminderListener.onCreated` (`@OnEvent(APPOINTMENT_EVENT.CREATED)`) ran
**after** `AppointmentsService.create`'s transaction committed, and needed
3-4 fresh reads (load the appointment, resolve reminder rules, check for
existing `ScheduledNotification` rows, insert new ones) — each checking out
its **own** connection from the same pool `create()` itself was just
competing for. Under saturation those reads lost the race for a connection
and `ReminderListener`'s own `try/catch` swallowed the failure (by design —
a reminder failure must never turn a successful booking into a failed HTTP
response), so the reminder was silently never scheduled. The load test
measured this directly: ~2.5% of bookings at saturated levels never got a
reminder. Webhook delivery and workflow runs never had this problem — both
already write a transactional `outbox_jobs` row inside the same transaction
that creates the triggering entity, so their queue publish is decoupled from
any post-commit read racing for a connection.

## Fix — reuse the existing outbox, no new architecture

Per the brief's own instruction ("smallest architecture-compatible reliable
mechanism... do not introduce a large messaging architecture unnecessarily")
and guardrail #3 (verify the existing mechanism first): the codebase already
has exactly the durability primitive this needs — `outbox_jobs` — used by
webhook delivery and workflow runs. This fix gives reminders the same
treatment, adding no new table, no new queue, no new relay.

1. **New job name `reminders.schedule`** (`src/queue/queue.constants.ts`),
   consumed by the existing `notifications.processor.ts` (the same
   processor `notifications.dispatch` and `notifications.reap` already run
   on) rather than a new processor class.
2. **`AppointmentsService.create`** (`src/modules/appointment/appointment.service.ts`,
   inside the existing `dataSource.transaction` block, immediately after the
   existing `writeHistory` call) now writes one `OutboxJob` row —
   `queue: NOTIFICATIONS`, `job_name: reminders.schedule`,
   `dedupe_key: reminders-schedule-<appointmentId>`,
   `payload: {tenantId, appointmentId}` — on the **same `manager`** the
   transaction already holds. No new connection, no new read: the write
   commits or rolls back atomically with the appointment and its other
   inserts, using work the transaction was already doing.
3. **`NotificationsProcessor.process`** gained a `reminders.schedule` branch
   (before the existing dispatch fallthrough) that validates the payload,
   runs inside the standard `runInTenantContext` tenant-scoping/
   authorization wrapper (matching every other job this processor handles),
   and calls the **same** `ReminderSchedulerService.scheduleFor` the
   listener already called — already idempotent via a unique `source_ref`
   per lead time, so a BullMQ retry after a transient failure safely
   schedules whatever lead times weren't claimed yet and no-ops the rest.
4. **`ReminderListener.onCreated` retired.** CONFIRMED/CANCELLED/COMPLETED/
   NO_SHOW/RESCHEDULED stay on the listener, deliberately: each of those is a
   one-appointment-at-a-time action triggered by a deliberate staff/patient
   step, never in the same booking-creation burst that caused the
   measured loss, and none of the five was ever observed to have this
   problem. Moving all six event handlers would have been unrelated,
   unmeasured scope.
5. **DLQ scope, deliberately smaller than the dispatch path's:** an
   exhausted `reminders.schedule` job (5 attempts, exponential backoff — the
   queue's existing default, unchanged) is logged but not parked in a DLQ.
   Five retries already closes the measured gap (zero retries today); a
   replay UI for this queue was judged out of scope — this finding never
   asked for one, and building it now would be exactly the "large messaging
   architecture" the brief said not to introduce unnecessarily.

## What was NOT changed

- No new table, no new queue, no new relay process — `outbox_jobs` and its
  existing worker-side relay are reused as-is.
- `ReminderSchedulerService.scheduleFor` itself — untouched; both the old
  listener path and the new outbox path call the identical idempotent
  method.
- CONFIRMED/CANCELLED/COMPLETED/NO_SHOW/RESCHEDULED reminder handling —
  still the listener, unchanged.
- Webhook/workflow outbox usage — untouched; this fix is additive on the
  same table.

## A real gap this work caught before it shipped

Adding the `reminders.schedule` branch to `NotificationsProcessor` means
every such job now calls `WorkerAuthorizationService.assertAuthorized`,
which fails **closed** on any job name absent from `JOB_AUTHZ_POLICY`
(`src/queue/job-authorization.constants.ts`) — by design
(§0.8.7/§0.8.10), so a forgotten registration is a silent 100%-failure mode,
not a silent skip. The existing `job-entitlement-coverage.spec.ts` (which
asserts every `JOB.*` name is registered) caught exactly this: the full
unit-suite run after the P1.5 code changes went from 4 pre-existing failing
suites to 5, the new one being this coverage test. **Fixed** by registering
`[JOB.REMINDERS_SCHEDULE]: { tier: 'tenant', featureKey:
FeatureKey.NOTIFICATIONS }` — the same tier and the same capability as its
sibling `notifications.dispatch`, since a `reminders.schedule` job only ever
produces the `ScheduledNotification` rows that flow through that exact
dispatch path. Re-verified: the full suite returned to exactly the same 4
pre-existing failures afterward (see Verification below). Without this
fix, the entire P1.5 mechanism would have shipped completely non-functional
— every real `reminders.schedule` job would have been rejected at the
authorization step, never reaching `scheduleFor` at all.

## A second, unrelated finding surfaced incidentally (not fixed — logged as FU-014)

Running the full `appointment-availability.e2e-spec.ts` file (to place the
new outbox e2e test in a realistic, already-populated suite rather than a
new file) surfaced one pre-existing failing test in that file —
`'allows any hour on a day with NO schedule configured while the clinic has
not opted in'` — expects `201`, gets `409 STAFF_NOT_AVAILABLE`. **Confirmed
unrelated to P1.5**: reproduces identically on the file's pre-P1.5 version
(`git stash` of only this file, same isolated single-test run) and in
complete isolation (`-t` selecting only that test, fresh `beforeAll`). Root
cause traced to `AvailabilityService.evaluate`'s deliberate "a staff member
with an explicit schedule on *some* days is not exempt on an uncovered day"
rule (`availability.service.ts:698-709`) interacting with the shared test
fixture, which always seeds one `StaffSchedule` row (Wednesday) for the
doctor — so the test can never actually reach the "zero schedule rows
anywhere" case its name claims to cover. Logged as **FU-014** in
`FOLLOWUP_FINDINGS.md` with full evidence and a recommended fix (give this
specific test a staff member with zero schedule rows). Not fixed here per
guardrail #11/scope control: `AvailabilityService`'s working-hours semantics
are unrelated to Reminder/Webhook Loss, and this is a test-fixture question,
not a production defect.

## Security / regression review (guardrail #9, #10)

- **No data loss:** the outbox row and the appointment row share one
  transaction — either both commit or neither does. Proven at both the unit
  level (mocked manager, rollback scenario) and the e2e level (real
  Postgres, real commit).
- **No tenant-isolation regression:** the `reminders.schedule` job carries
  `tenantId` in its payload and now runs through the same
  `runInTenantContext`/`WorkerAuthorizationService` tenant-scoping gate
  every other job in this processor already uses — actually a strictly
  *stronger* guarantee than the retired listener path had (the listener
  never passed through worker-level tenant authorization at all).
- **No appointment-overlap regression:** nothing here touches the booking
  window, availability evaluation, or the `appointments_no_overlap`
  exclusion constraint.
- **No payment/billing regression:** not applicable — this phase touches
  only post-booking reminder scheduling.
- **No security control weakened:** no bcrypt/authorization/constraint
  change in this phase; the one authorization-registry change *adds* a gate
  that didn't exist on the retired listener path, it does not relax one.
