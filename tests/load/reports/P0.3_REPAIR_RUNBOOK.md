# P0.3 — Repair runbook

**For an operator repairing a production or production-like database.**
Written 2026-09-03. Nothing in this file has been executed against production;
production has never been inspected.

Read `P0.3_SCHEMA_REMEDIATION_PLAN.md` first for *why*. This is *how*.

**Three rules that override anything else in this document:**

1. **Never delete a row to make DDL succeed.** If a guard cannot be installed
   because of conflicting data, that is information, not an obstacle. §3.
2. **A migration that succeeds locally is not evidence.** The local databases
   are missing up to 23 guards and hold at most 900,000 rows. §5.
3. **Stop at the first surprise.** Every step below is individually reversible;
   a half-understood sequence is not.

---

## 1. Prechecks

### 1.1 Find out what you actually have

```bash
psql "$DATABASE_URL" -f tests/load/reports/P0.3_PRODUCTION_VERIFICATION.sql \
  | tee p03-$(date +%Y%m%d-%H%M).log
```

Read-only: `pg_catalog`, `information_schema`, and row counts in §5. No INSERT,
UPDATE, DELETE or persistent DDL. It creates three session-local TEMP views.

§5 aggregates over the tables backing each guard — seconds to minutes on
multi-million-row tables, competing for I/O. It takes no lock that blocks
writers. **Prefer a read replica or a quiet window.** To skip it entirely, stop
after §4; §1–§4 are catalog-only and near-instant.

The one line to read first:

```
P03_STATUS=ENFORCED  P0_PASS=18 P0_FAIL=0 ... ENFORCED_TOTAL=43 TOTAL=43
```

| status | meaning | then |
|---|---|---|
| `ENFORCED` | every guard present and matching | **stop.** No repair needed. Go to §7 and wire this into CI |
| `REVIEW` | all present; some renamed or differently defined | read §3 of the output. `ENFORCED_RENAMED` is not a defect in what the database accepts — see §1.3 |
| `DEGRADED` | some P1 guards absent, no P0 | §2 onward |
| `CRITICAL` | **at least one P0 guard absent** | §2 onward, and treat as an incident: the application is the only thing preventing duplicate charges, replayed webhooks or duplicate accounts |

### 1.2 Read §5 before planning anything

§5 tells you which missing guards are one-line repairs and which are blocked:

```
NOTICE:  clear     UQ_integration_oauth_states_state    0 conflicts - installable now
NOTICE:  BLOCKED   UQ_subscription_usage_...            189 excess rows in subscription_usage
```

Every `BLOCKED` line is a §3 decision **before** any migration is written. A
migration that tries to install a blocked guard will abort — which is the
correct behaviour, but you would rather know now.

### 1.3 `ENFORCED_RENAMED` is not damage to repair

TypeORM renames every index it recreates from entity metadata to
`IDX_<28 hex>`. The rule survives; the name does not. The script reports these
separately and names the index actually in use.

**Do not "fix" one by creating the canonically-named index** — you will end up
with two identical unique indexes, doubling write cost for nothing. If you want
the canonical name, `ALTER INDEX "IDX_..." RENAME TO "UQ_..."` is instant and
takes only a brief ACCESS EXCLUSIVE lock. It also tells you something: a schema
with renamed guards was touched by the synchronizer at some point, so ask how.

### 1.4 Confirm synchronize cannot run here

```bash
psql "$DATABASE_URL" -c "SELECT count(*) FROM public.migrations;"   # must be > 0
```

Any value > 0 means the app now refuses to boot with `TYPEORM_SYNCHRONIZE=true`
against this database (P03-013), independently of `NODE_ENV`. If it is 0 on a
database you believe is migration-managed, **stop** — you are connected to the
wrong database.

## 2. Backups

Nothing in §4 changes data, and every migration there is reversible by dropping
one object. Take a backup anyway, because §3 and §6 are not reversible.

```bash
pg_dump --format=custom --no-owner --file=pre-p03-$(date +%Y%m%d).dump "$DATABASE_URL"
pg_restore --list pre-p03-*.dump | head            # verify it is readable
```

For a blocked-guard repair (§3), a full dump is not enough on its own —
capture the specific rows you are about to change so they can be reasoned about
afterwards without a full restore:

```sql
CREATE TABLE p03_backup_subscription_usage AS
  SELECT *, now() AS captured_at FROM subscription_usage WHERE subscription_id IS NULL;
```

## 3. Conflicting data — the decision that cannot be automated

**Applies to every `BLOCKED` line in §5 of the verification output.**

`CREATE UNIQUE INDEX` fails while duplicates exist. So a blocked guard is a
one-way door: it stays absent, duplicates keep accumulating, and every boot
reports the same error. Someone must decide which rows are real.

**What you must NOT do**, however tempting under pressure:

- `DELETE ... USING ... WHERE a.ctid > b.ctid` — this is exactly what the old
  bootstraps did (P03-002). `ctid` is the row's physical location; PostgreSQL
  changes it on any UPDATE and on `VACUUM FULL`, so the survivor is arbitrary
  and not reproducible.
- `CREATE INDEX` without `UNIQUE` to make the error go away. The guard then
  exists in name and enforces nothing — the exact failure P0.1 warns about.
- Dropping the constraint from the migration so the deploy passes.

### 3.1 The known case: `UQ_subscription_usage_tenant_period_unsubscribed`

Observed on the dev database, 2026-09-03. **Check whether production has it
before assuming anything** — this may be dev-only.

```
189 excess rows across 17 (tenant_id, period_month) keys. Worst key: 180 rows.
```

Root cause (P03-001): synchronize dropped `subscription_usage.subscription_id`
and re-added it empty, orphaning 206 usage rows from their subscriptions. They
then all matched the guard's `WHERE subscription_id IS NULL` predicate, and the
guard was gone, so the idempotent upsert stopped conflicting.

First, establish the shape of the problem:

```sql
SELECT tenant_id, period_month, count(*) AS rows,
       sum(ai_tokens_used)  AS sum_ai,   max(ai_tokens_used)  AS max_ai,
       sum(appointments_used) AS sum_appt, max(appointments_used) AS max_appt,
       min(updated_at) AS first_seen, max(updated_at) AS last_seen
  FROM subscription_usage
 WHERE subscription_id IS NULL
 GROUP BY 1,2 HAVING count(*) > 1
 ORDER BY 3 DESC;
```

Then choose, deliberately:

| option | what it means | when it is right | cost |
|---|---|---|---|
| **A. Sum the counters** | the rows are fragments of one month's usage that failed to upsert | the counters look like increments (many small values) | over-counts if any row was itself a running total |
| **B. Keep the maximum per counter** | each row is a snapshot of a running total; the largest is the latest | the counters look like cumulative totals | under-counts if they are genuinely separate increments |
| **C. Keep the newest row by `updated_at`, archive the rest** | the last writer wins | you cannot tell A from B, and the numbers are advisory rather than billed | discards real usage |

**Whichever you choose, do it in this order** — and note that the reconciliation
step is a genuine `UPDATE`, so it is not reversible without §2's side table:

```sql
BEGIN;
-- 1. archive first, always
CREATE TABLE p03_backup_subscription_usage AS
  SELECT *, now() AS captured_at FROM subscription_usage WHERE subscription_id IS NULL;

-- 2. reconcile (option A shown; adapt for B or C)
WITH merged AS (
  SELECT tenant_id, period_month,
         sum(ai_tokens_used) ai, sum(whatsapp_messages_used) wa,
         sum(appointments_used) appt, sum(campaigns_used) camp,
         min(id) AS keep_id
    FROM subscription_usage WHERE subscription_id IS NULL
   GROUP BY 1,2 HAVING count(*) > 1)
UPDATE subscription_usage u
   SET ai_tokens_used = m.ai, whatsapp_messages_used = m.wa,
       appointments_used = m.appt, campaigns_used = m.camp
  FROM merged m WHERE u.id = m.keep_id;

DELETE FROM subscription_usage u USING (
  SELECT tenant_id, period_month, min(id) AS keep_id
    FROM subscription_usage WHERE subscription_id IS NULL
   GROUP BY 1,2 HAVING count(*) > 1) m
 WHERE u.tenant_id = m.tenant_id AND u.period_month = m.period_month
   AND u.subscription_id IS NULL AND u.id <> m.keep_id;

-- 3. prove it worked BEFORE committing
SELECT count(*) AS remaining_conflicts FROM (
  SELECT 1 FROM subscription_usage WHERE subscription_id IS NULL
   GROUP BY tenant_id, period_month HAVING count(*) > 1) x;
-- must be 0. If not: ROLLBACK.
COMMIT;
```

The survivor is chosen by `min(id)` — a stable, reproducible key — not by
`ctid`. Only then install the guard (§4).

### 3.2 Orphaned foreign-key references

Before any `ADD CONSTRAINT ... FOREIGN KEY`:

```sql
SELECT count(*) FROM <table> x
 WHERE x.<col> IS NOT NULL
   AND NOT EXISTS (SELECT 1 FROM tenants t WHERE t.id = x.<col>);
```

Observed on dev: `verification_audit_logs` 6, `tenant_counters` 1 (P03-008).

An audit table is the case to think hardest about. `ON DELETE CASCADE` deletes
the audit trail along with the tenant, which is usually precisely what an audit
trail must not do. `ON DELETE SET NULL`, or no FK plus a documented retention
policy, is often the better answer. Decide before you migrate.

## 4. Installing missing guards

One migration per guard. Copy the structure of
`src/migrations/1730088000000-AppointmentNoOverlapRepair.ts` — it is the worked
example this project already has, and it gets four things right:

1. **Idempotent early return** if the object already exists (so it is safe on a
   database that already has it).
2. **A conflict pre-check that counts and aborts**, never deletes.
3. **`RAISE EXCEPTION` with every count inside the MESSAGE.** node-postgres
   surfaces only `error.message` through `QueryFailedError`, so `DETAIL` and
   `HINT` are invisible from the CLI. Anything you put there is lost.
4. **A post-condition assert** that the object now exists.

### 4.1 Lock, duration and reversal per form

| you are installing | write this | lock | blocks writers? | reverse |
|---|---|---|---|---|
| a unique **index** | `CREATE UNIQUE INDEX CONCURRENTLY` | SHARE UPDATE EXCLUSIVE | **no** | `DROP INDEX CONCURRENTLY` |
| a unique **constraint** | `CREATE UNIQUE INDEX CONCURRENTLY`, then `ADD CONSTRAINT ... UNIQUE USING INDEX` | brief ACCESS EXCLUSIVE to attach | momentarily | `DROP CONSTRAINT` |
| a **CHECK** | `ADD CONSTRAINT ... CHECK ... NOT VALID`, then `VALIDATE CONSTRAINT` | brief ACCESS EXCLUSIVE, then SHARE UPDATE EXCLUSIVE | **no** | `DROP CONSTRAINT` |
| a **foreign key** | `ADD CONSTRAINT ... FOREIGN KEY ... NOT VALID`, then `VALIDATE CONSTRAINT` | as above, on **both** tables | **no** | `DROP CONSTRAINT` |
| an **EXCLUDE** | `ADD CONSTRAINT ... EXCLUDE USING gist` | **ACCESS EXCLUSIVE, whole build** | **YES** | `DROP CONSTRAINT` |
| a **column type change** | `ALTER COLUMN ... TYPE uuid USING col::uuid` | **ACCESS EXCLUSIVE, full rewrite** | **YES** | **restore from backup** |

`CONCURRENTLY` cannot run inside a transaction block, so the migration must set:

```ts
export class X implements MigrationInterface {
  public transaction = false;   // required for CONCURRENTLY
  // ...
}
```

This project already has three migrations that do exactly this —
`1730019000000-CustomerTenantScopedEmail.ts` is the clearest. Copy its shape.

A failed concurrent build leaves an **INVALID** index behind. Find and drop it
before retrying:

```sql
SELECT c.relname FROM pg_index i JOIN pg_class c ON c.oid = i.indexrelid
 WHERE NOT i.indisvalid;
```

### 4.2 The one that needs a maintenance window

`appointments_no_overlap`. PostgreSQL has no `CONCURRENTLY` and no `NOT VALID`
form for an exclusion constraint, so installing one holds ACCESS EXCLUSIVE for
the whole build: every read and write on `appointments` waits.

**Measured (P0.1): 15.16 s on 900,000 rows.** Scale from your own row count:

```sql
SELECT count(*) FROM appointments WHERE deleted_at IS NULL;
```

Always set a lock timeout, so the attempt fails fast rather than queueing behind
a long-running transaction and blocking the table for everyone:

```sql
SET lock_timeout = '5s';
SET statement_timeout = '10min';
```

And check nothing is already holding a long transaction on that table:

```sql
SELECT pid, state, now()-xact_start AS age, left(query, 80)
  FROM pg_stat_activity
 WHERE xact_start IS NOT NULL AND now()-xact_start > interval '30 s'
 ORDER BY age DESC;
```

## 5. Migration order

1. **Guards with 0 conflicts, index form first.** Each is independent, online,
   and reversible by dropping one object. Deploy in batches, verify between.
2. **CHECK constraints.** `NOT VALID` first, `VALIDATE` in a separate migration
   so a slow validation never blocks the deploy.
3. **Foreign keys**, with an orphan pre-check that aborts (§3.2). Adopt the six
   entity-declared ones from the plan §6.3; leave the two telemetry FKs pending
   a write-cost measurement.
4. **`appointments_no_overlap`**, alone, in a maintenance window (§4.2).
5. **Column type changes**, last, individually, each with its own backup.

Between every batch:

```bash
psql "$DATABASE_URL" -f tests/load/reports/P0.3_PRODUCTION_VERIFICATION.sql | grep P03_STATUS
```

**Do not batch a data repair (§3) with a schema migration.** If the schema
change fails you want to roll it back without also reverting a data decision.

## 6. Rehearsal — and why local is not one

The local databases are missing up to 23 guards, so a migration that "worked
locally" may simply have skipped the object that would have failed. Two local
facts make that concrete: `PatientActionLinks1730063000000` aborts with
`relation "patient_action_links" already exists` on a synchronize-built database
(P03-004), and no local database exceeds 900,000 rows in any table.

Rehearse on a restored production dump:

```bash
createdb rehearsal
pg_restore --no-owner --dbname=rehearsal pre-p03-*.dump
psql -d rehearsal -f tests/load/reports/P0.3_PRODUCTION_VERIFICATION.sql | grep P03_STATUS
#   ... run the full sequence here, timing each step ...
psql -d rehearsal -f tests/load/reports/P0.3_PRODUCTION_VERIFICATION.sql | grep P03_STATUS
dropdb rehearsal
```

**Time each step on the rehearsal database and use those numbers to size the
window.** Do not use the numbers in this document — they come from databases
orders of magnitude smaller than production.

Also verify the chain still builds every guard from empty, which is the check
that catches a migration you broke while writing the repair:

```bash
npx jest --config test/jest-integration.json test/integration/schema-contract.int-spec.ts
```

## 7. Post-deployment verification

```bash
# 1. the schema
psql "$DATABASE_URL" -f tests/load/reports/P0.3_PRODUCTION_VERIFICATION.sql | grep P03_STATUS
#    expect: P03_STATUS=ENFORCED ... TOTAL=43

# 2. the application agrees — counts only, no object names (the route is public)
curl -s "$APP_URL/api/v1/system/health/readiness" | jq .schemaGuards
#    expect: {"status":"ok","requiredChecked":21,"requiredFailed":0}

# 3. no guard reported a problem at boot
grep -c "INTEGRITY GUARD" <application log>
#    expect: 0
```

All three must agree. If §1 says `ENFORCED` and readiness says `degraded`, the
instance is running against a **different database** than the one you just
checked — verify `DATABASE_URL` before anything else.

Then, for a week: alert on `INTEGRITY GUARD` at ERROR in the application log,
and on `schemaGuards.status != "ok"`. Both are new in P0.3 and both mean a
DB-enforced guarantee the application depends on is not in place.

## 8. Rollback

| what you did | how to undo it |
|---|---|
| installed a unique index | `DROP INDEX CONCURRENTLY "name";` — instant, no data change |
| installed a constraint (UNIQUE / CHECK / FK / EXCLUDE) | `ALTER TABLE t DROP CONSTRAINT "name";` — instant, no data change |
| a failed `CONCURRENTLY` build | find the INVALID index (§4.1), drop it, retry |
| deployed the P0.3 code | revert the commit. **Note:** the pre-P0.3 bootstraps deleted duplicate rows on every boot; reverting restores that behaviour |
| tripped the migrated-DB synchronize guard on a box that needs it | `TYPEORM_SYNCHRONIZE_ALLOW_MIGRATED_DB=true` — no deploy needed |
| readiness now returns 503 | `SCHEMA_GUARD_FAIL_READINESS=false` (its default) |
| **a data repair (§3)** | **not reversible.** Restore the rows from `p03_backup_*`, or from the §2 dump |
| **a column type change** | **not reversible in place.** Restore from the §2 dump |

**If a migration fails mid-run:** `migrationsTransactionMode: 'each'` means each
migration commits independently, so earlier ones stay applied and the failed one
rolled back entirely. Fix the cause and re-run — do not hand-edit the
`migrations` table. A migration recorded as applied whose DDL never ran is
exactly the P0.1 defect that started this whole line of work, and it is
invisible to everything except `P0.3_PRODUCTION_VERIFICATION.sql`.
