# P1.2 — Authentication CPU Herd Remediation

**Date:** 2026-09-04. Root cause confirmed, fixed, measured before/after.
**Bcrypt cost is unchanged (12) — this fixes the implementation, not the
hashing strength.**

---

## Root cause (MS-008, confirmed against current code, not assumed)

`src/modules/auth/auth.service.ts` imported **`bcryptjs`** (pure JS), not
native `bcrypt`. `bcryptjs`'s async API still executes the Blowfish rounds
on Node's single JS thread — it does not use libuv's threadpool the way
native `bcrypt` does — so a burst of concurrent logins serializes real CPU
work directly on the event loop that also serves every other request.

## Fix

Replaced `bcryptjs` with native `bcrypt` (N-API, libuv threadpool) across
every call site: `auth.service.ts`, `patient.service.ts`, three seed files,
and the test files that mock/import it directly (`auth.service.spec.ts`,
`patient.service.spec.ts`, `all-misc.spec.ts`, `all-services.spec.ts`,
`test/login-protection.e2e-spec.ts`, `test/auth-abuse-redis-degradation.e2e-spec.ts`,
`test/utils/auth-concurrency-fixtures.ts`). `package.json`:
`bcryptjs`/`@types/bcryptjs` removed, `bcrypt@6.0.0`/`@types/bcrypt@6.0.0`
added. **`BCRYPT_ROUNDS = 12` unchanged everywhere.**

### Feasibility verified before committing to the swap, not assumed

- **Prebuild on the exact deploy image:** `docker run node:24.11-alpine3.22`
  (the Dockerfile's own base) — `npm install bcrypt` completed in ~2s (a
  prebuilt binary, no compilation) and `hashSync`/`compareSync` worked.
- **Cross-compatibility, both directions, on real hashes:** native `bcrypt`
  correctly verifies (and correctly rejects a wrong password against) a
  hash `bcryptjs` produced — every existing user's stored password still
  works. `bcryptjs` also correctly verifies a hash native `bcrypt` produces
  — rollback safety, if this ever needs reverting. Both libraries produce
  `$2b$` hashes; format is identical.
- **Local dev machine (Windows):** also verified working, independent of
  the Alpine/Docker check above.

## Measured before/after (the actual claim, not an assumption)

50 concurrent password compares, same machine (the `node:24.11-alpine3.22`
container used for the feasibility check above), same password/hash, same
cost factor (12):

| | `bcryptjs` (before) | native `bcrypt` (after) |
|---|---|---|
| Wall-clock for 50 concurrent compares | 16,147 ms | 3,106 ms |
| **Max event-loop lag during the burst** | **5,041 ms** | **1 ms** |

The event-loop-lag number is the one that matters for MS-008 — it is
literally "how long was every other request on this process stalled while
logins were happening", and it drops from ~5 seconds to effectively zero.
The wall-clock improvement (5.2×) is a secondary benefit of libuv
threadpool parallelism across cores; not the primary fix.

**Not re-measured against the original 400-VU load-test scenario** — the
50-concurrent microbenchmark above isolates the bcrypt call itself, which
is what actually changed; re-running the full k6 soak scenario is a much
larger undertaking than this specific finding needs and was not judged
necessary to prove the fix works. If a full soak re-run is wanted later,
`tests/load/` already has the scenario (`soak.js`) that originally surfaced
MS-008.

## Also fixed in the same file (`auth.service.ts`), directly related

1. **±10% jitter on the access-token TTL** (`issueTokens`). Addresses
   MS-008's actual *trigger*, not just its cost: a population of clients
   that authenticated together (normal traffic, or every session
   invalidated at once by a deploy or a Redis flush) previously expired
   together too, producing exactly the synchronized mass-reauth burst the
   load test measured. Freshly randomized on every token issuance (not
   derived from the user id) — the goal is de-synchronizing a *cohort's*
   expiry moments. A base TTL of `0` (the pre-existing, deliberately-tested
   defensive fallback for an unparseable `JWT_ACCESS_TTL`) is left exactly
   `0`, never jittered up — verified by a dedicated regression test.
   Consolidating the JWT `sign()` call and the reported `expiresIn` onto one
   computed value also closes a latent inconsistency: previously the actual
   signed token used the *raw config string* while the reported
   `expiresIn` used a separately-computed ms value, which could only ever
   silently diverge if `ttlToMs`'s parsing and `jsonwebtoken`'s own `ms()`
   parsing of the same string ever disagreed even slightly.
2. **Targeted `UPDATE` for `last_login_at`**, replacing a full-entity
   `.save()` on the object `validateCredentials` loaded (which includes
   `password_hash` — a full save re-writes it for no reason on every
   login).
3. **Diagnostic warning when >1 active user shares an email** in
   `validateCredentials`. `uq_user_email_global` (a P0 guard, curated in
   `critical-schema-guards.json`, verified `ENFORCED` in production per
   P0.4) makes this case impossible today; if it is ever seen, that guard is
   missing — a free, request-time second signal alongside `SchemaGuardCatalogService`
   (P0.5), not a replacement for it. The candidate loop itself is
   unchanged in shape — it still tries every active candidate (never
   assumes at most one), so the pre-`uq_user_email_global` "email shared
   across clinics, password disambiguates" case the method's own docstring
   describes still works if that guard is ever legitimately absent.

## Deliberately NOT done, and why

- **No new login throttle added.** Investigated and rejected: MS-008's
  actual scenario is many *different* legitimate accounts logging in
  around the same time (a cohort re-authenticating), not repeated attempts
  against *one* account — which the existing per-email 5-failure/900s
  lockout (`LoginProtectionService`) and the global 300/min/IP
  `ThrottlerGuard` already cover for their respective threats. A new
  per-account throttle would not have prevented MS-008's scenario (it isn't
  the same account being hit) and risks locking out legitimate users during
  exactly the mass-reauth event it's meant to help with. The two real fixes
  for that scenario are (1) making bcrypt cheap on the event loop — done —
  and (2) jitter, so a cohort doesn't expire in lockstep in the first place
  — done.
- **Bcrypt cost factor unchanged (12).** Never a candidate for change —
  cost 12 is a security parameter, not a performance one.
- **Full soak-scenario re-run** — see above; the targeted microbenchmark is
  what actually isolates this fix's effect.
