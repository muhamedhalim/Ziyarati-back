## SCHEMA-001 — A single `synchronize` boot destroys 32 integrity guards; only the bootstrap-backed ones survive

**Severity:** **Critical** (dev/test only — see production impact)
**Flags:** `SYNCHRONIZE_VULNERABLE`, `BOOTSTRAP_DEPENDENCY`

**Exact objects.** 21 UNIQUE indexes, 10 CHECK constraints, 1 UNIQUE
constraint. The complete list is §1–§2 of `P0.2_SCHEMA_INVENTORY.md`. The ones
that matter most:

| object | what stops being true |
|---|---|
| `uq_user_email_global` | two accounts can share a login email |
| `ck_user_email_lowercase` | …and differ only by case, defeating any application-level check |
| `UQ_resource_purchases_tenant_idempotency` | a retried purchase charges twice |
| `UQ_sub_invoice_webhook_event` | a replayed billing webhook creates a second invoice |
| `UQ_sub_invoice_period` | two non-void invoices for one period |
| `UQ_integration_inbound_events_replay` | an inbound webhook can be replayed |
| `UQ_integration_oauth_states_state` | an OAuth state can be replayed |
| `UQ_email_suppressions_tenant_email` | an unsubscribe can be duplicated/contradicted |
| `CHK_resource_purchases_*` (5) | negative or zero quantities, prices and unit sizes are accepted |

**Evidence.** Controlled experiment on a disposable database:

```
createdb p02_audit → node dist/src/migrate.js run   →  133 migrations applied
snapshot A         →  454 indexes, 1,474 constraints
boot dist/src/main with TYPEORM_SYNCHRONIZE=true (once)
snapshot B         →  381 indexes, 1,440 constraints
```

Compared **functionally** (table + columns + predicate), not by name, because
synchronize renames what it recreates:

| | functionally lost |
|---|---|
| indexes | **77** — of which **21 UNIQUE** (integrity) and 56 performance |
| constraints | **50** — of which **10 CHECK**, 1 UNIQUE, 10 FK, 29 NOT NULL |

Snapshot B was re-taken later and was byte-identical, so these are **net**
losses after every bootstrap had finished — not a transient window.

**Root cause.** `TYPEORM_SYNCHRONIZE=true` does two things in
`src/config/typeorm.config.ts`: it skips the migration chain
(`if (!synchronize) { await runMigrationsWithAdvisoryLock(…) }`) *and* enables
TypeORM's schema synchronizer, whose `dropOldIndices()` / `dropOldExclusions()`
/ `dropOldChecks()` remove every object absent from entity metadata. During the
boot the synchronizer issued **178 `DROP INDEX`** and **120 `DROP CONSTRAINT`**
statements.

**The rule that decides survival** — visible directly in the inventory: an
object survives **iff** some module's `OnApplicationBootstrap` re-issues it as
`CREATE … IF NOT EXISTS`. 32 objects are re-created that way (including
`uq_refund_idem`, `uq_txn_webhook_event`, `uq_message_wa_id` — the three named
in the brief). Everything migration-only is gone. Survival is therefore an
accident of which module happens to own a bootstrap, not a property of how
important the guard is: refund idempotency survives, *purchase* idempotency
does not.

**Affected environments.** dev **15/43** critical guards present · perf **24/43**
· perf_t2 **33/43** · e2e **43/43** · synchronize control **15/43**. The dev
database matches the control exactly, which is what a synchronize-damaged
schema looks like.

**Production impact.** **None directly** — `synchronize` is forced off and is a
hard boot error under `NODE_ENV=production` (verified, SCHEMA-008). The
production impact is *indirect and real*: dev and CI run against a schema that
enforces materially less than production, so a test suite cannot detect a
missing guard, and a developer cannot reproduce a production constraint
violation. It also means **no local environment is a valid rehearsal for a
production data migration.**

**Recommended remediation** (P0.3, not done here — pick one):
1. **Preferred:** set `TYPEORM_SYNCHRONIZE=false` in the tracked `.env` and let
   migrations own every schema, everywhere. This deletes the entire failure
   class, including SCHEMA-002/003/005.
2. Declare the survivors in entity metadata (`@Index({ unique, where })`,
   `@Check`, `@Exclusion` — the P0.1 fix generalised). Closes the drop, but
   each object must be declared and kept in step by hand.
3. Keep synchronize and add a bootstrap for all 32 — cheapest, worst: it
   entrenches SCHEMA-004 and leaves survival dependent on module load order.

**Migration requirement.** None for production (production is not damaged).
Local databases need `npm run migration:run` against a **rebuilt** database —
the migrations are already recorded, so re-running repairs nothing (this is
P0.1's DRIFT-002). A rebuild-from-empty is the only reliable repair.

**Verification command.**
```bash
psql "$DATABASE_URL" -f tests/load/reports/P0.2_PRODUCTION_VERIFICATION.sql
```

## SCHEMA-002 — `synchronize` drops and re-adds 23 columns, destroying their data, including a clinical audit trail

**Severity:** **Critical** (dev/test only)
**Flags:** `SYNCHRONIZE_VULNERABLE`

**Exact objects.** 23 `DROP COLUMN` statements. It is not a rename: TypeORM
emits `DROP COLUMN` then `ADD`, so every value is lost and the new column is
empty (or filled with a default).

```
clinical_entry_revisions  DROP COLUMN "changed_byId"  → ADD "changedById" uuid
clinical_entry_revisions  DROP COLUMN "created_at"    → ADD "created_at" TIMESTAMP NOT NULL DEFAULT now()
clinical_entries          DROP COLUMN "created_at" / "updated_at" / "deleted_at"
clinical_encounters       DROP COLUMN "created_at" / "updated_at"
clinical_access_logs      DROP COLUMN "created_at"
customer_segments         DROP COLUMN "created_byId" / "created_at" / "updated_at" / "deleted_at"
subscription_usage        DROP COLUMN "subscription_id"
ai_messages               DROP COLUMN "agent_user_id"
merchant_accounts         DROP COLUMN "created_at" / "updated_at"
integration_inbound_events        DROP COLUMN "received_at" / "updated_at"
integration_oauth_states          DROP COLUMN "created_at"
integration_staff_provisioning    DROP COLUMN "created_at" / "updated_at"
integration_webhook_endpoints     DROP COLUMN "created_at" / "updated_at"
```

**Evidence.** Captured verbatim from the boot's SQL log
(`tests/load/reports/p02/synchronize-ddl.log`). `clinical_entry_revisions` is
the revision history of clinical records: the boot erases **who** changed each
entry (`changed_byId`) and resets **when** (`created_at`) to boot time.
`subscription_usage.subscription_id` links usage to the subscription being
billed. `deleted_at` columns are dropped and re-added empty, which
**un-deletes every soft-deleted row** in `clinical_entries` and
`customer_segments`.

**Root cause.** The entity's property name (`changedById`) and the migration's
column name (`changed_byId`) disagree. TypeORM sees an unknown column and a
missing one, and has no rename detection — it drops and adds.

**Affected environments.** Any database booted with `TYPEORM_SYNCHRONIZE=true`
that holds data — i.e. the dev database on every `npm run start`.

**Production impact.** **None directly** (synchronize cannot run there). But the
column names genuinely differ between dev and production, so any raw SQL,
report, export or data-fix script referencing `created_byId` /`changed_byId`
works in production and fails in dev, and vice versa.

**Recommended remediation.** Same as SCHEMA-001 remediation 1. Separately,
reconcile the naming: either rename the columns in a migration to match the
entities, or add explicit `@Column({ name: 'created_byId' })` mappings so the
two agree. **Do not** let a synchronize boot perform the reconciliation.

**Migration requirement.** If the entity names are chosen as canonical, one
additive migration per column using `ALTER TABLE … RENAME COLUMN` (which
preserves data) — never DROP/ADD.

**Verification command.**
```bash
psql "$DATABASE_URL" -c "SELECT table_name, column_name FROM information_schema.columns WHERE table_schema='public' AND column_name IN ('created_byId','createdById','changed_byId','changedById') ORDER BY 1,2;"
```

## SCHEMA-003 — `synchronize` makes 29 NOT NULL columns nullable, 11 of them tenant keys

**Severity:** **High** (dev/test only)
**Flags:** `SYNCHRONIZE_VULNERABLE`

**Exact objects.** 28 `ALTER COLUMN … DROP NOT NULL` statements plus one column
lost entirely. Tenant keys affected: `clinical_access_logs.tenantId`,
`clinical_encounters.tenantId`, `clinical_entries.tenantId`,
`clinical_entry_revisions.tenantId`, `customer_segments.tenantId`,
`email_suppressions.tenant_id`, `patient_action_links.tenantId`,
`queue_entries.tenantId`, `waitlist_entries.tenantId`,
`waitlist_offers.tenantId`. Also every FK on `queue_entries`,
`waitlist_entries`, `waitlist_offers` and the clinical tables.

**Evidence.** Full list in the boot SQL log; the schema diff shows
`CONSTRAINT|n` count falling by 29.

**Root cause.** The entity relations are declared without `nullable: false`, so
TypeORM's metadata says nullable and the synchronizer relaxes the column to
match.

**Affected environments.** Dev and any synchronize-booted database.

**Production impact.** **None directly.** The risk is inverted: a row with a
NULL `tenantId` cannot exist in production but can in dev, so tenant-isolation
logic exercised locally is exercised against data shapes production forbids —
and a bug that *creates* such a row is invisible locally.

**Recommended remediation.** SCHEMA-001 remediation 1, or add
`nullable: false` to the affected relations so entity metadata matches the
migrations.

**Migration requirement.** None for production (already NOT NULL there).

**Verification command.**
```bash
psql "$DATABASE_URL" -c "SELECT table_name, column_name FROM information_schema.columns WHERE table_schema='public' AND column_name IN ('tenantId','tenant_id') AND is_nullable='YES' ORDER BY 1;"
```

## SCHEMA-004 — The bootstraps that hold the money-critical guards fail silently

**Severity:** **High**
**Flags:** `BOOTSTRAP_DEPENDENCY`

**Exact object.** `PaymentsSchemaBootstrap.run()` and the equivalent in the
other seven bootstrap services:

```ts
private async run(label: string, sql: string): Promise<void> {
  try { await this.dataSource.query(sql); }
  catch (err) { this.logger.warn(`Skipped "${label}": ${(err as Error).message}`); }
}
```

**Evidence.** A `warn`, and boot continues. These bootstraps own
`uq_refund_idem`, `uq_txn_webhook_event`, `uq_payments_appointment_pending`,
`uq_refund_gateway_id`, `uq_message_wa_id`, `uq_message_status`,
`uq_ai_tool_call_idem`, `uq_settlement_adj_refund` and the two
`tenant_entitlement_ledger` guards — i.e. exactly the objects SCHEMA-001 shows
surviving *only* because of them.

**Root cause.** Deliberate ("fails SOFT per statement so a permissions hiccup
never blocks startup") — a reasonable default for a *supplementary* index, and
the wrong one for a uniqueness guard. Compounding it: `CREATE UNIQUE INDEX IF
NOT EXISTS` **fails when the table already contains duplicates**. So the
sequence "guard missing → duplicates accumulate → bootstrap can never succeed
again" is self-locking, and every attempt logs one `warn` line.

**Affected environments.** All, production included — this code runs on every
boot regardless of `NODE_ENV`.

**Production impact.** **Real, and the most production-relevant finding in
P0.2.** In production these guards exist because their migration ran, so the
bootstrap is a no-op today. But it is also the *only* self-repair path, and it
is one that cannot report its own failure. If a guard is ever absent in
production, the system will not tell you.

**Recommended remediation.** Split the failure policy by intent: a *uniqueness
or integrity* statement must log at `error` and increment a metric (and be
listed in the P0.2 verification script); a *performance index* may stay soft.
Do not make bootstraps fatal — a clinic mid-day is worse off with a dead API.

**Migration requirement.** None. Code change only.

**Verification command.**
```bash
grep -rn "Skipped \"" logs/ | grep -iE "unique|idem|dedup"    # any hit = a guard failed to install
psql "$DATABASE_URL" -f tests/load/reports/P0.2_PRODUCTION_VERIFICATION.sql
```

## SCHEMA-005 — Dev and production enforce different foreign keys, in both directions

**Severity:** **High**
**Flags:** `MIGRATION_MISSING_BUT_OBJECT_EXISTS`, `SYNCHRONIZE_VULNERABLE`, `DEFINITION_MISMATCH`

**Exact objects.** FK totals match (297 = 297) but the *sets* differ by 10 each
way.

**Present in dev/test, absent in production (10)** — dev is stricter:
`ai_execution_metrics.tenantId`, `ai_memories.tenantId`, `workflows.tenantId`,
`workflow_runs.tenantId`, `support_tickets.tenantId`,
`customer_segments.tenantId`, `customer_segments.createdById`,
`clinical_entry_revisions.changedById`, `customer_notes.conversationId`,
`handover_requests.transferred_from_id` — all → their parent tables.

**Present in production, absent in dev/test (10)** — production is stricter:
`ai_batch_items.batch_job_id` (ON DELETE CASCADE), `ai_batch_items.tenant_id`,
`ai_batch_jobs.tenant_id`, `tenant_ai_deployments.tenant_id`,
`api_logs.api_key_id`, `patient_action_links.waitlist_offer`,
`customer_segments.tenantId` **ON DELETE CASCADE**,
`customer_segments.created_byId` **ON DELETE SET NULL**,
`support_tickets.tenantId` **ON DELETE CASCADE**,
`clinical_entry_revisions.changed_byId`.

**Evidence.** Structural comparison (table + full FK definition, names ignored)
of snapshots A and B.

**Root cause.** Two independent causes. (a) Entity relations that no migration
mirrors — `workflows.tenantId` is a `ManyToOne` in metadata and has no FK in any
migration, so only synchronize creates it. (b) The column renames of SCHEMA-002
carry their FKs with them.

**The referential-action divergence is the sharpest edge:** deleting a tenant
**cascades** in production (`customer_segments`, `support_tickets`) and is
**blocked** in dev. A tenant-deletion routine tested locally will behave
differently in production — silently, and destructively.

**Affected environments.** dev/test vs production.

**Production impact.** **Real.** Production genuinely lacks a FK on
`workflows.tenantId`, `workflow_runs.tenantId`, `ai_memories.tenantId`,
`ai_execution_metrics.tenantId` and `support_tickets.tenantId`/
`customer_segments.tenantId` (under those column names). Orphaned
tenant-scoped rows are possible there and impossible locally.

**Recommended remediation.** Decide the canonical set per table, then write
migrations for the ones production should have. **Do not** add a FK to a
high-volume append-only telemetry table (`ai_execution_metrics`, `api_logs`)
without measuring the write cost first — those omissions may well be
deliberate; this audit could not find a document saying so either way.

**Migration requirement.** One additive migration per FK adopted, each with a
pre-check for orphaned rows that aborts rather than deleting (the
`AppointmentNoOverlapRepair` pattern from P0.1).

**Verification command.**
```bash
psql "$DATABASE_URL" -f tests/load/reports/P0.2_PRODUCTION_VERIFICATION.sql   # § TENANT ISOLATION
```

## SCHEMA-006 — 13 tenant-scoped tables have no foreign key to `tenants` in the canonical schema

**Severity:** **Medium**
**Flags:** (canonical — not drift)

**Exact objects.** On the reference database `ziyarati_e2e` (43/43 guards
present, migration-built): `admin_notifications`, `ai_execution_metrics`,
`ai_memories`, `ai_tool_calls`, `email_logs`, `free_access_overrides`,
`settlement_adjustments`, `subscription_invoices`, `subscription_usage`,
`tenant_counters`, `verification_audit_logs`, `workflow_runs`, `workflows` —
each has a `tenantId`/`tenant_id` column and **no FK to `tenants(id)`**.

**Evidence.** The TENANT ISOLATION section of the verification script, run
against the clean reference database. This is **not** synchronize damage — it is
what the migration chain builds.

**Root cause.** Mixed. Several are raw-SQL, entity-less tables created
deliberately to avoid `synchronize` churn (their own docstrings say so:
`settlement_adjustments`, `tenant_entitlement_ledger`, `free_access_overrides`).
For those, the missing FK is a side effect of dodging synchronize — i.e. a
second-order cost of SCHEMA-001. For `workflows`/`workflow_runs` the entity
declares the relation and no migration creates the FK (SCHEMA-005a).

**Affected environments.** All, production included.

**Production impact.** Rows can reference a tenant that does not exist, and
deleting a tenant leaves orphans in billing (`subscription_invoices`,
`subscription_usage`), entitlements (`free_access_overrides`) and business
configuration (`workflows`). Nothing observed says this has happened; the audit
establishes that nothing prevents it.

**Recommended remediation.** Triage into "deliberate (telemetry/append-only,
document the decision)" and "should have a FK". Add FKs only to the second
group.

**Migration requirement.** Additive migration per adopted FK, with an orphan
pre-check that aborts.

**Verification command.** As SCHEMA-005.

## SCHEMA-007 — The migration CLI performs no environment validation, so a mistyped `NODE_ENV` disables TLS verification

**Severity:** **Medium**
**Flags:** (configuration)

**Exact objects.** `src/migrate.ts` → `src/config/data-source.ts` →
`databaseSslOptions(process.env)`.

**Evidence.** `migrate.ts`'s own docstring: *"Reads configuration from the
process environment ONLY"*. It never calls `validate` from
`src/config/env.validation.ts`. `databaseSslOptions` returns `false` — no
certificate verification at all — for any `NODE_ENV` that is not the exact
string `production`. Measured through the compiled factory: `NODE_ENV` values
`PRODUCTION`, `production ` (trailing space) and `prod` all take the
non-production branch.

**Root cause.** Exact, case-sensitive string comparison plus a code path that
deliberately sits outside the Nest/ConfigModule graph.

**Affected environments.** Any deployment that runs migrations as a separate
release step (the documented pattern in `migrate.ts` for Railway / Fly / ECS /
Kubernetes Jobs).

**Production impact.** A typo in the migration job's environment — a different
place from the API's environment, and easy to set independently — causes the
migration connection to skip certificate verification while still succeeding.
It does **not** enable `synchronize` (`data-source.ts` hardcodes
`synchronize: false`), so schema damage is not possible by this route.

**Recommended remediation.** Either run `validate()` at the top of
`migrate.ts`, or normalise (`String(env.NODE_ENV).trim().toLowerCase()`) inside
`databaseSslOptions` and treat an unrecognised value as production (fail
closed).

**Migration requirement.** None. Code change only.

**Verification command.**
```bash
# In the migration job's own environment:
node -e "console.log(JSON.stringify(process.env.NODE_ENV))"   # must print exactly "production"
```

## SCHEMA-008 — The production `synchronize` guard works, but nothing tests it

**Severity:** **Medium**
**Flags:** (test coverage)

**Evidence — the guard itself PASSES.** Driving the real compiled
`typeOrmFactory` across an environment matrix:

| NODE_ENV | TYPEORM_SYNCHRONIZE | role | result |
|---|---|---|---|
| `production` | `true` | api | **THROWS** `❌ TypeORM synchronize is NOT allowed in production` |
| `production` | `true` | **worker** | **THROWS** — same guard, both process roots |
| `production` | `false` / unset / `TRUE` / `1` | api | proceeds; `synchronize=false`; migrations run |
| `development` / `test` / unset | `true` | api & worker | `synchronize=true`, migrations skipped |

Also confirmed: `migrationsRun: false` always — migrations are run explicitly by
`runMigrationsWithAdvisoryLock` before the DataSource is built, not by TypeORM;
all three other `DataSource` constructions (`config/data-source.ts`,
`run-migrations-with-lock.ts`, `seed/data-source.ts`) hardcode or default
`synchronize: false`; and `NODE_ENV` reaching the factory is the **Joi-validated**
value, restricted to `development|production|test`, so the case-sensitivity
weakness in SCHEMA-007 is not reachable through a normal API/worker boot.

**The finding is the absence of a test.** `src/config/typeorm.config.spec.ts`
has 14 cases covering pool timeouts and the metrics logger, and **none**
asserting the production guard. The single most important safety property of
this file is unprotected against a future refactor.

**Production impact.** None today. The exposure is regression risk.

**Recommended remediation.** Add three cases to the existing spec: production +
`true` throws (api), the same for `worker`, and production + `false` yields
`synchronize: false`.

**Migration requirement.** None.

**Verification command.**
```bash
npx jest src/config/typeorm.config.spec.ts
```

## SCHEMA-009 — The three long-lived local databases each enforce a different schema

**Severity:** **Medium**
**Flags:** `MIGRATION_SAYS_APPLIED_BUT_OBJECT_MISSING`

**Evidence.** The same 43-object check against every reachable database:

| database | migrations recorded | critical guards present | verdict |
|---|---|---|---|
| `ziyarati_e2e` | 132 | **43 / 43** | **ENFORCED** |
| `ziyarati_perf_t2` | 75 | 33 / 43 | CRITICAL — 5 P0 absent |
| `ziyarati_perf` | 133 | 24 / 43 | CRITICAL — 4 P0 absent |
| `ziyarati` (dev) | 118 | 15 / 43 | CRITICAL — 7 P0 absent |
| `p02_audit` (control) | 133 | 15 / 43 | CRITICAL — 7 P0 absent |

`ziyarati_perf` records **133** migrations — every one, including P0.1's repair —
and is still missing `uq_user_email_global`, `ck_user_email_lowercase`,
`UQ_integration_inbound_events_replay` and `UQ_integration_oauth_states_state`.
That is the P0.1 drift signature exactly: recorded as applied, not present.

Dev's 15/43 is **identical** to the controlled synchronize-damaged database,
which is what makes the attribution unambiguous.

**Production impact.** Indirect but concrete: the load tests in
`MASSIVE_SCALE_LOAD_TEST_REPORT.md` and the P0.1 contention tests ran against
`ziyarati_perf`, a database missing 19 of 43 integrity guards. It does **not**
invalidate those results — they measured the appointment path, and
`appointments_no_overlap` was independently verified present for every one of
those runs — but no load test against that database can be read as evidence
about any *other* guard.

**Recommended remediation.** Rebuild the local databases from empty via the
migration chain, the way `test/setup-e2e-db.js` already builds the one database
that passes. Then stop booting anything with `synchronize` against them.

**Migration requirement.** None — rebuild, because re-running recorded
migrations repairs nothing (P0.1 DRIFT-002).

**Verification command.** As SCHEMA-001.

## SCHEMA-010 — `UQ_customers_tenant_email` has a different definition in `ziyarati_perf_t2`

**Severity:** **Low**
**Flags:** `DEFINITION_MISMATCH`

**Exact object.**

```
canonical: CREATE UNIQUE INDEX "UQ_customers_tenant_email" ON public.customers
             USING btree ("tenantId", email) WHERE (deleted_at IS NULL)
perf_t2:   CREATE UNIQUE INDEX "UQ_customers_tenant_email" ON public.customers
             USING btree ("tenantId", email)
```

**Evidence.** The DEFINITION DIFFERS row from the verification script.

**Root cause.** Not established. `ziyarati_perf_t2` has only 75 migration rows,
so it predates the migration that added the partial predicate; the index was
presumably created by an earlier version and never rebuilt.

**Production impact.** None (lab database). The finding matters as a
demonstration that the verification script detects *definition* drift, not only
absence: the perf_t2 index is **stricter** than canonical — a soft-deleted
customer's email can never be reused there, but can be in production. A test
written against perf_t2 would encode the wrong behaviour.

**Recommended remediation.** Rebuild `ziyarati_perf_t2` (SCHEMA-009).

**Migration requirement.** None.

**Verification command.** As SCHEMA-001.
