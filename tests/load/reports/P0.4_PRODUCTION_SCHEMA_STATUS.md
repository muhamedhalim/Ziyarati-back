### P04-001 — An instance reports READY while 30 of 43 guards, 8 of them P0, are absent

**Severity: P1** (observability; it does not itself weaken the database)
**Answers STEP 12 directly.**

`SchemaGuardRegistry` records the outcome of statements a **bootstrap
attempted**. Nothing else. So `GET /api/v1/system/health/readiness` can only
ever report on the 13 curated guards that have a bootstrap. The other 30 —
migration-owned, no runtime re-creation — are never looked at by any running
process, and their absence produces `status: "ok"`.

The eight P0 guards in that blind spot:

```
appointments_no_overlap                    UQ_sub_invoice_period
uq_user_email_global                       UQ_sub_invoice_webhook_event
ck_user_email_lowercase                    UQ_resource_purchases_tenant_idempotency
UQ_integration_oauth_states_state          UQ_integration_inbound_events_replay
```

That list is precisely the set P0.2 measured a synchronize boot destroying, and
precisely the set the dev database is missing today. If production is missing
any of them, **no running instance will say so.**

`appointments_no_overlap` is the sharpest case, because the codebase *already
detects it*: `SchedulingIntegrityService.onApplicationBootstrap()` checks for
the constraint on every boot and logs at `error` when it is gone — it did so
throughout the entire P0 campaign (P0.1 DRIFT-003). It simply does not report
into `SchemaGuardRegistry`, so the signal never reaches readiness. Wiring that
one service into the registry is a three-line change and closes the most
important row in the table.

**Evidence.** `test/fixtures/critical-schema-guards.json` (43 entries) matched
against every `*bootstrap*.ts` in `src/`, comments stripped: 13 named, 30 not.
Full list in `P0.4_PRODUCTION_VERIFICATION_RAW.md § 4`.

**Not fixed here** — P0.4 is read-only, and STEP 12 says *"Do not change
readiness behavior in this phase."* Repair designed in
`P0.4_PRODUCTION_REPAIR_PLAN.md § 2`.

### P04-002 — `TYPEORM_SYNCHRONIZE_ALLOW_MIGRATED_DB` is a global boolean, so it waives the P0.3 guard for whatever database it happens to be pointed at

**Severity: P1** · **Answers STEP 11's specific question.**
**This is a weakness in P0.3's own fix, reported against it.**

P0.3 added a guard that refuses `synchronize` against any database whose
`migrations` table holds a row — closing the middle ground `NODE_ENV` cannot
see (staging, QA, demo, restored backups). It also added an override so the
existing local workflow kept working, because P03-004 proved the obvious
alternative fails. The override is a plain boolean, and it waives the guard for
*any* target.

**Measured, driving the real compiled factory across 13 cases:**

| NODE_ENV | SYNC | OVERRIDE | target | outcome |
|---|---|---|---|---|
| `production` | true | **true** | migrated | **REFUSED** — `TypeORM synchronize is NOT allowed in production` |
| `production` | true | true | migrated | **REFUSED** — worker root, same |
| `PRODUCTION` / `prod` / `staging` | true | true | migrated | **REFUSED** — unrecognised values fail closed |
| `development` | true | false | migrated | **REFUSED** — `target database has 3 applied migration(s)` |
| `development` | true | **true** | **migrated** | **ALLOWED, synchronize=true** ← the hole |
| `test` | true | true | migrated | **ALLOWED, synchronize=true** |
| *(unset)* | true | true | migrated | **ALLOWED, synchronize=true** |
| `development` | true | either | virgin | ALLOWED — the ordinary local workflow, untouched |

**So: can it accidentally be enabled in a real persistent environment?**

- **Not in production.** Proven above, both process roots, and for every
  mistyped spelling of the value. The `NODE_ENV=production` guard runs *first*
  and the override cannot reach it. This is a hard structural bound, not a
  policy.
- **Yes anywhere else.** Staging, QA, demo, a shared team box or a restored
  backup — booted as `development`, `test`, or with `NODE_ENV` unset — is
  waivable, which is exactly the population P03-013 was written to protect.

**The realistic accident path is specific:** P0.3 set
`TYPEORM_SYNCHRONIZE_ALLOW_MIGRATED_DB=true` in this repository's own `.env`,
because the dev database needs it. That file is gitignored, so it does not
propagate through git — but it propagates by being copied to a server, and by a
developer repointing their local `DATABASE_URL` at a shared database while the
override is still on. The tracked contract `.env.example` correctly ships
`false`, and the Joi default is `false`.

**Cost if it happens:** what P0.2 measured — 178 `DROP INDEX`, 120
`DROP CONSTRAINT`, 23 `DROP COLUMN`, 28 `DROP NOT NULL`, and the data in 23
columns including a clinical audit trail.

**Safer design proposed** (not implemented — STEP 11 says *"Do NOT change
production configuration during this audit"*): bind the waiver to the target
instead of making it global. `P0.4_PRODUCTION_REPAIR_PLAN.md § 1` carries the
code; the shape is that the value must **name the database it waives** and the
host must be loopback, so a `.env` copied anywhere else waives nothing. This
repository's current `.env` (`127.0.0.1:5433/ziyarati`) satisfies both, so the
local workflow does not change.

### P04-003 — The public readiness route returns raw database driver errors to anonymous callers

**Severity: P2 (Low)** · **Answers STEP 12's leak question.**
**Pre-existing; not introduced by P0.3.**

`GET /api/v1/system/health/readiness` is `@Public()`. When the database ping
fails it returns `db.reason?.message` verbatim. Measured against `pg`, that
message is one of:

```
connect ECONNREFUSED 127.0.0.1:5999
password authentication failed for user "postgres"
database "no_such_db" does not exist
```

— internal host and port, the database username, or the database name, to an
unauthenticated caller. `DEPLOYMENT.md § 6` documents this route as the
traffic-admission probe and does not say it should be internal-only.

The `schemaGuards` block that P0.3 added to the same payload is deliberately
counts-only and leaks nothing; this finding is about the `database`/`redis`
branches that predate it. Exposure is limited: the message only appears when the
datastore is already down.

**No guard drift on production (operator-run):** all 43 objects exist under

- **The governing lesson from P0.1 still applies and is why this phase exists:**
  a row in the `migrations` table proves a migration once ran, not that its
  effect still exists. §4 of the verification script is the only thing that can
  settle it for production.

## Data integrity risk — evidence of prior destructive synchronize impact

**Partly answered by the operator-run result.** The guard-level signature —
TypeORM hash-named replacements — is absent (`P0_RENAMED=0`, `P1_RENAMED=0`),
which is the strongest available evidence that no synchronize boot has ever
touched production. The column-level signatures (dropped/re-added columns,
NOT NULL loss) were not in the operator's report and remain **not verified**;
the two direct queries in the handover below settle them if ever needed.

One thing about production data integrity **is** settled, and it is a change P0.3
already made: until 2026-09-03 three `OnApplicationBootstrap` services ran
unconditional `DELETE` statements on every application start **in every
environment, production included** — on `messages` (patient conversations),
`message_status_logs` and `dashboard_metrics`, choosing the survivor by `ctid`.
That code shipped and ran. It is now replaced by count-and-report pre-checks
(P03-002), so the ongoing loss has stopped.

**How much was destroyed in production before that, and when, is unknown and is
not recoverable from the schema** — the deletions were unlogged and unreported.
A rough lower bound can be recovered from backups if a retention window still
covers the period: compare `count(*)` on `messages` at two backup points against
the application's own inserted-message count. That is an investigation, not a
verification, and it is out of scope here.

## Handover — what the operator needs to run

> **Done — 2026-09-04.** The operator ran the script; the result is recorded at
> the top of this document. The instructions are kept for re-runs (post-deploy
> verification, incident triage).

```bash
psql "$DATABASE_URL" -f tests/load/reports/P0.3_PRODUCTION_VERIFICATION.sql \
  | tee p04-prod-$(date +%Y%m%d-%H%M).log
```

Proven read-only in this phase — see § 2 of the RAW file. It executes 14 SQL
statements and 27 psql meta-commands, creates 5 **session-local TEMP views**,
and runs 43 `SELECT count(*)` conflict checks. It issues no `INSERT`, `UPDATE`,
`DELETE`, `ALTER`, `DROP`, `CREATE` (non-TEMP), `TRUNCATE`, `GRANT`, `REVOKE`,
`VACUUM` or `REINDEX`, and no `\copy`, `\i`, `\o` or `\!`.

**Cost:** §1–§4 are catalog-only and near-instant. **§5 aggregates over the
tables backing each failing guard** — seconds to minutes on multi-million-row
tables, competing for I/O, taking no lock that blocks writers. Prefer a read
replica or a quiet window; stop after §4 to skip it entirely.

**Read this line first:**

```
P03_STATUS=ENFORCED  P0_PASS=18 P0_FAIL=0 ... ENFORCED_TOTAL=43 TOTAL=43
```

| status | means | next |
|---|---|---|
| `ENFORCED` | all 43 present and matching | **stop.** Nothing to repair. Wire the script into CI and proceed to P1 work |
| `REVIEW` | all present; some renamed or differently defined | `ENFORCED_RENAMED` is not damage — see runbook §1.3. **Do not** create the canonically-named index alongside it |
| `DEGRADED` | some P1 guards absent, no P0 | `P0.4_PRODUCTION_REPAIR_PLAN.md § 3` |
| `CRITICAL` | **≥1 P0 guard absent** | treat as an incident. The application is the only thing preventing duplicate charges, replayed webhooks or duplicate accounts. **Do not start P1 performance work** |

Three checks that are *not* in the script and are worth running in the same
session, because they distinguish "never had it" from "had it and lost it":

```sql
-- 1. Has anything ever synchronized here? Hash-named indexes are the fingerprint.
SELECT count(*) FROM pg_indexes
 WHERE schemaname='public' AND indexname ~ '^IDX_[0-9a-f]{26,}$';

-- 2. The DROP COLUMN + ADD signature: a gap in attnum with the column re-added last.
SELECT attrelid::regclass AS table, attname, attnum FROM pg_attribute
 WHERE attrelid IN ('subscription_usage'::regclass, 'clinical_entry_revisions'::regclass)
   AND attnum > 0 AND NOT attisdropped ORDER BY 1, 3;

-- 3. Migration history depth — compare with the file count in src/migrations/.
SELECT count(*) AS applied, max(name) AS latest FROM public.migrations;
```

Expected on an untouched migration-built database: **0** for the first;
`subscription_usage.subscription_id` at ordinal **3** for the second (dev has it
at 10, with 3 missing — that is the damage signature).
