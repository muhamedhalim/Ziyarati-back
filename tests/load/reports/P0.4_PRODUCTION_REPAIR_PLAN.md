**Date:** 2026-09-04. **Nothing in this file has been executed.**
**No production data or schema was modified.**

Read `P0.4_PRODUCTION_SCHEMA_STATUS.md` first for what was and was not
established.

This file has two halves, and the split matters:

- **§1–§2 are actionable now.** They are the two production-code issues this
  phase proved. Neither needs a production connection to fix, and neither
  touches the database.
- **§3 is conditional.** Every production *schema* repair depends on output

**The three rules from `P0.3_REPAIR_RUNBOOK.md` govern everything here:**
never delete a row to make DDL succeed; a migration that succeeds locally is
not evidence; stop at the first surprise.

## 1. P04-002 — Bind the synchronize waiver to its target

**Exact issue.** `TYPEORM_SYNCHRONIZE_ALLOW_MIGRATED_DB=true` waives P0.3's
migrated-database guard for whatever `DATABASE_URL` happens to point at. Proven
by driving the compiled factory: refused under `production`/`PRODUCTION`/
`prod`/`staging`, allowed under `development`/`test`/unset.

**Affected objects.** `src/config/typeorm.config.ts`
(`assertSynchronizeIsSafeForTarget`, `SYNCHRONIZE_MIGRATED_DB_OVERRIDE`),
`src/config/env.validation.ts`, `.env.example`, this repository's `.env`.

**Affected rows/counts.** None — no data. The *risk* it carries is what P0.2
measured for one waived boot: 178 `DROP INDEX`, 120 `DROP CONSTRAINT`, 23
`DROP COLUMN`, 28 `DROP NOT NULL`, and the data in 23 columns including
`clinical_entry_revisions.changed_byId` (a clinical audit trail) and
`subscription_usage.subscription_id`.

**Business impact.** Bounded, and the bound is worth stating precisely: it
**cannot** affect a `NODE_ENV=production` deployment, because the production
guard runs first and the override cannot reach it. It can destroy a staging,
QA, demo, shared-team or restored-backup database — which costs rebuild time
and, if that database held anything not reproducible, the data.

**Deterministic repair strategy.** Make the waiver name what it waives, and
require the target to be local. A value of `true` stops being accepted.

```ts
// Replaces the boolean check at the top of assertSynchronizeIsSafeForTarget.
//
// A global boolean waives the guard for whatever DATABASE_URL currently points
// at — including a database the operator never intended to name. Requiring the
// value to BE the database name, and the host to be loopback, means an .env
// copied to another machine or repointed at a shared database waives nothing:
// the name will not match, or the host will not be local.
const waiver = String(config.get<string>(SYNCHRONIZE_MIGRATED_DB_OVERRIDE) ?? '').trim();
if (waiver) {
  const { hostname, pathname } = new URL(databaseUrl);
  const target = pathname.replace(/^\//, '');
  const isLoopback = ['localhost', '127.0.0.1', '::1', '[::1]'].includes(hostname);
  if (waiver === 'true') {
    throw new Error(
      `❌ ${SYNCHRONIZE_MIGRATED_DB_OVERRIDE}=true is no longer accepted — a global waiver ` +
        `applies to whatever DATABASE_URL points at. Set it to the database name it may ` +
        `waive (here: "${target}"), and only for a database on this machine.`,
    );
  }
  if (waiver !== target) {
    throw new Error(
      `❌ ${SYNCHRONIZE_MIGRATED_DB_OVERRIDE}="${waiver}" but DATABASE_URL names "${target}". ` +
        `The waiver does not apply to this database. Refusing to synchronize.`,
    );
  }
  if (!isLoopback) {
    throw new Error(
      `❌ ${SYNCHRONIZE_MIGRATED_DB_OVERRIDE} names "${target}", but its host is "${hostname}", ` +
        `not this machine. The waiver exists for a local development database only.`,
    );
  }
  logger.warn(
    `⚠️ ${SYNCHRONIZE_MIGRATED_DB_OVERRIDE}=${target} — synchronize is permitted against the ` +
      `LOCAL migration-provisioned database "${target}". Objects not described by entity ` +
      `metadata may be DROPPED on this boot.`,
  );
  return;
}
```

Then `.env` becomes `TYPEORM_SYNCHRONIZE_ALLOW_MIGRATED_DB=ziyarati`, and the
Joi rule changes from `valid('true','false')` to a database-name pattern with
`.default('')`.

**Verified precondition:** this repository's `.env` is
`127.0.0.1:5433/ziyarati`, so it satisfies both conditions and the local
workflow does not change.

**Known trade-off, stated rather than hidden.** The loopback condition breaks
one legitimate case: a developer running the app *inside* Docker Compose, where
`DATABASE_URL` names a service (`postgres:5432`) rather than loopback. That
configuration exists in this repository only in `docker-compose.prod.yml`,
which sets `NODE_ENV=production` and therefore never reaches this code. If a
non-production compose workflow is added later, the loopback test needs a
documented second form — not a removal.

**Required migration.** None. Code and configuration only.
**Lock behavior.** None.
**Downtime requirement.** None.
**Backup requirement.** None.

**Verification.**
```bash
npx jest src/config/typeorm.config.spec.ts
npx jest --config test/jest-integration.json test/integration/synchronize-guard.int-spec.ts
npm run start   # must still boot against the local dev database
```
Add three cases to `synchronize-guard.int-spec.ts`: `=true` is refused; a
non-matching name is refused; a matching name on a non-loopback host is refused.

**Rollback/recovery.** Revert the commit. The previous boolean form still works.

**Owner/business decision required.** None — this is a hardening choice inside
one file. It is only *not* done here because STEP 11 says *"Do NOT change
production configuration during this audit."*

## 2. P04-001 — Make the readiness signal cover the guards it claims to

**Exact issue.** `SchemaGuardRegistry` only records statements a bootstrap
attempted, so `GET /system/health/readiness` reports on 13 of 43 curated
guards. 30 — including 8 P0 — return `status: "ok"` whether present or absent.

**Affected objects.** `src/config/schema-guard.registry.ts`,
`src/modules/scheduling/scheduling-integrity.service.ts`,
`src/health/health.controller.ts`, `test/fixtures/critical-schema-guards.json`.

**Affected rows/counts.** None — no data. 30 guards unobserved, 8 of them P0.

**Business impact.** If production is missing a P0 guard today, nothing running
will say so. That is the condition P0.1 found in the dev database and did not
notice for the length of an entire load-test campaign, during which the
contention arm proved nothing it claimed to prove.

**Deterministic repair strategy — in two steps, smallest first.**

**2a. Wire the one detector that already exists.** `SchedulingIntegrityService`
already checks `appointments_no_overlap` on every boot and logs at `error`
(P0.1 DRIFT-003). Inject `SchemaGuardRegistry` and report the result. Three
lines; closes the single most important row in the table.

**2b. Add a boot-time catalog assertion for the other 29.** A read-only check
against `pg_catalog`, driven by `test/fixtures/critical-schema-guards.json` —
the same fixture `schema-contract.int-spec.ts` already uses, so the list has
exactly one home. It must compare by **shape** (uniqueness, table, columns,
predicate), not by name, or it will report `ENFORCED_RENAMED` guards as missing
and send an operator to install an index that already exists (P03-005).

Cost is one catalog query at boot, no table access. It reports; it does not
create — nothing at runtime should be issuing DDL to repair a guard.

**Required migration.** None. Code only.
**Lock behavior.** None — `pg_catalog` reads.
**Downtime requirement.** None. Keep the default `SCHEMA_GUARD_FAIL_READINESS=false`:
turning a missing index into a fleet-wide 503 converts an integrity problem into
an outage.
**Backup requirement.** None.

**Verification.** Extend `schema-contract.int-spec.ts`: build a database from
empty, drop one P0 guard, assert `summary()` reports `degraded` and names it in
`failures()` but not in `summary()`. The contract test was already proven
falsifiable in P0.3; this keeps that property.

**Rollback/recovery.** Revert. Readiness returns to today's behaviour.

**Owner/business decision required.** One: whether a production instance
missing a P0 guard should refuse traffic (`SCHEMA_GUARD_FAIL_READINESS=true`)
or serve while reporting `degraded`. The default answer here is *serve* — a
clinic mid-day is worse off with a dead API than with a missing index — but
that is a business call, not an engineering one.

## 2c. P04-003 — Stop returning driver errors on the public readiness route

**Exact issue.** `db.reason?.message` and `redis.reason?.message` are returned
verbatim on a `@Public()` route. Measured: `connect ECONNREFUSED <host>:<port>`,
`password authentication failed for user "<user>"`, `database "<name>" does not
exist`.

**Repair.** Return a fixed string (`"unreachable"`) in the body and log the
detail. The `schemaGuards` block added in P0.3 is already shaped this way and
is the pattern to copy.

**Severity P2**, listed here because it is one line in the same file as §2 and
should ride along rather than become its own ticket. No migration, no lock, no
downtime, no backup. Verification: the existing health spec, with the expected
payload updated.

## 3. Conditional plan for production schema repair

**Nothing below can be turned into a migration until
`P0.3_PRODUCTION_VERIFICATION.sql` has been run against production.** These are
the branches, with the work each implies.

### 3.1 If `P03_STATUS=ENFORCED` — **← SELECTED (operator-run result, 2026-09-04)**

Production reported `ENFORCED`, 43/43, no renames, no mismatches, no §5
conflicts (recorded in `P0.4_PRODUCTION_SCHEMA_STATUS.md`). §3.2–§3.5 below are
therefore **not applicable** and are kept only as the record of what would have
been done.

All 43 present and matching. **No repair.** Two follow-ups:

1. Wire the script into CI as a post-deploy gate — it already emits one
   greppable `P03_STATUS=` line for exactly this. (There is no CI pipeline in
   this repository today; that is the first task, not the second.)
2. Proceed to P1 scalability work. The P0 line is clear.

### 3.2 If `P03_STATUS=REVIEW`

Every guard enforced, some under TypeORM hash names (`ENFORCED_RENAMED`) or
with a different definition.

- **A renamed guard is not damage.** Do **not** create the canonically-named
  index alongside it — that yields two identical unique indexes and doubles
  write cost. `ALTER INDEX "IDX_..." RENAME TO "UQ_..."` is instant if the name
  is wanted (`P0.3_REPAIR_RUNBOOK.md § 1.3`).
- **But ask how it got there.** A hash-named guard in production means the
  synchronizer touched that database at some point. That is a bigger question
  than the index, and it changes the priority of §1 from hardening to incident
  response.
- A **definition** mismatch is different from a rename and must be read
  individually: `P0.2 SCHEMA-010` showed a perf database whose
  `UQ_customers_tenant_email` was *stricter* than canonical.

### 3.3 If `P03_STATUS=DEGRADED` (P1 guards absent, no P0)

Order, per `P0.3_REPAIR_RUNBOOK.md § 5`:

1. Read §5 of the output first. Every `BLOCKED` line is a business decision
   *before* any migration is written.
2. Guards with **0 conflicts**: one migration each,
   `CREATE UNIQUE INDEX CONCURRENTLY`, `public transaction = false`, copying
   `1730088000000-AppointmentNoOverlapRepair.ts` — idempotent early return,
   conflict pre-check that **aborts rather than deletes**, counts inside the
   `RAISE EXCEPTION` message (node-postgres discards `DETAIL` and `HINT`), and
   a post-condition assert. SHARE UPDATE EXCLUSIVE; does not block writers.
3. Re-run the script between batches.

### 3.4 If `P03_STATUS=CRITICAL` (≥1 P0 guard absent)

**Stop and treat it as an incident before writing any migration.** A missing P0
guard means the application is the only thing preventing duplicate charges,
replayed webhooks or duplicate accounts — and it has been for an unknown period.

1. **Establish the window.** Which guard, and since when. The `migrations` row
   will say the migration ran; that is not evidence it still exists (P0.1
   DRIFT-002). The hash-named-index query in the status document's *Handover*
   section distinguishes "never created" from "created and dropped".
2. **Look for the damage the absence permits, before installing the guard** —
   because installing it first destroys the evidence of how many duplicates
   there were. §5 of the script gives the count per guard.
3. **Only then install**, per §3.3.

Two P0 cases need their own handling:

- **`appointments_no_overlap`** — the only guard with no online installation
  path. PostgreSQL offers no `CONCURRENTLY` and no `NOT VALID` form for an
  EXCLUDE constraint, so it holds **ACCESS EXCLUSIVE for the entire build**:
  every read and write on `appointments` waits. **Measured: 15.16 s on 900,000
  rows (P0.1).** Scale from `SELECT count(*) FROM appointments WHERE deleted_at
  IS NULL`. Maintenance window; `SET lock_timeout='5s'` so the attempt fails
  fast instead of queueing behind a long transaction and blocking the table for
  everyone; check `pg_stat_activity` for long transactions first.
- **`uq_user_email_global` + `ck_user_email_lowercase`** — these two are a
  pair. Installing the unique index without the lowercase CHECK leaves two
  accounts able to differ only by case. Install the CHECK
  (`NOT VALID`, then `VALIDATE` in a separate migration) **first**, then the
  index.

### 3.5 If §5 reports any `BLOCKED` guard

**Do not repair it. Do not choose a survivor.** Report: table, logical key,
duplicate count, affected tenants, and the deterministic options.
`P0.3_REPAIR_RUNBOOK.md § 3` carries the worked example, including the three
costed options for `subscription_usage` and the explicit list of what must not
be done (`ctid` deletion, a non-unique index to silence the error, dropping the
constraint from the migration to make the deploy pass).

The survivor must be chosen by a stable key such as `min(id)`, never `ctid` —
PostgreSQL changes `ctid` on any `UPDATE` and on `VACUUM FULL`, so a `ctid`
choice is not reproducible. That is exactly what the three bootstraps P0.3
removed were doing.

### 3.6 Foreign keys and tenant isolation — deferred by design

Six entity-declared FKs are missing from the canonical schema and six canonical
FKs are absent from a synchronize-built one (P03-007). **No migration should be
written for any of them until production's actual FK set is known** — the whole
point of P03-007 was that the two schemas disagree in *both* directions, so
"copy dev into production" is the wrong instinct in half the cases.

`subscription_invoices.tenant_id` and `subscription_usage.tenant_id` are
`character varying` in the canonical schema, so a tenant FK on those two
requires `ALTER COLUMN ... TYPE uuid` — an **ACCESS EXCLUSIVE full table
rewrite**, not reversible in place, needing its own backup and window. It is
last in any order, individually, never batched.

Any FK migration needs an orphan pre-check that **aborts**:

```sql
SELECT count(*) FROM <table> x
 WHERE x.<col> IS NOT NULL
   AND NOT EXISTS (SELECT 1 FROM tenants t WHERE t.id = x.<col>);
```

Dev has 6 orphans in `verification_audit_logs` and 1 in `tenant_counters`
(P03-008). Whether an **audit** table should carry a cascading FK is a design
question in its own right: `ON DELETE CASCADE` deletes the audit trail along
with the tenant, which is usually precisely what an audit trail must not do.

## 4. What this plan deliberately does not contain

| not here | why |
|---|---|
| Concrete repair migrations | The starting schema is unknown. A migration written against a guessed state is the P0.1 error repeated. |
| A `subscription_usage` reconciliation | RULE 9. It is a billing decision; the three costed options are in `P0.3_REPAIR_RUNBOOK.md § 3.1`. And it may not exist in production at all — its cause was a synchronize boot, which production has never had. |
| Restoring the 56 performance indexes | RULE 13: only indexes proven necessary. No measurement in this campaign establishes that for any individual one. They return with a rebuild. |
| Renaming the 23 drifted columns | Needs a decision on which naming is canonical, and every rename must be `ALTER TABLE ... RENAME COLUMN` (preserves data), never DROP/ADD. |
| A CI pipeline | There is none in this repository. Adding one is a separate piece of work; the verification script is already shaped for it. |
