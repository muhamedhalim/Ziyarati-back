# P1.1 — API Process Scaling Capacity Worksheet

**Date:** 2026-09-04. Documentation + boot-time estimator only — no runtime
behavior change (`API_CLUSTER_WORKERS` stays default `1` everywhere;
nothing in this repo sets it).

---

## What already exists (PERF-INFRA-003, built and validated 2026-08-10)

`src/cluster-bootstrap.ts` forks the API entrypoint via Node's built-in
`cluster` module when `API_CLUSTER_WORKERS > 1`. Confirmed safe to fork
(inspection, not assumption — see the file's own docstring): BullMQ
processors and the repeatable-job registrar live only in `WorkerModule`,
never in the API's own module graph; migrations serialize behind a Postgres
advisory lock across every process root and replica; every schema bootstrap
uses `IF NOT EXISTS`/`CREATE OR REPLACE` under a try/catch; the Socket.IO
gateway already uses a Redis-backed adapter for horizontal scale; payment
idempotency is a DB unique constraint, not in-process state.

**Measured (docs/PERFORMANCE_INFRASTRUCTURE.md PERF-INFRA-003, on this
machine, not re-measured this phase):** on a CPU-bound endpoint at n=50
concurrent requests, 4 processes vs 1 dropped p50 from 994.9ms to 540.6ms
and raised throughput from 40.49 to 50.30 req/s. Real cross-process
concurrency validated for Socket.IO transport affinity and Linux SIGTERM
graceful shutdown (a separate Linux container, not this Windows dev box).

## What this phase changed

`cluster-bootstrap.ts`'s boot-time connection estimate now uses the fuller
formula, and compares against a real ceiling when one is supplied:

```
estimated peak connections = API_CLUSTER_WORKERS × API_DB_POOL_MAX × 2
                              + WORKER_DB_POOL_MAX
```

**Why ×2 on the API term only:** a rolling restart briefly runs the OLD and
NEW set of API workers at once — the orchestrator keeps the old ones
accepting connections until the new ones report healthy — so steady-state
demand understates the real peak by roughly double, on the API side
specifically. The worker root is a single long-lived process per
deployment (not typically rolled the same way), so its own pool is not
doubled in this formula.

New optional env var `DB_MAX_CONNECTIONS` (informational only — this
application has no way to read Postgres's own setting) lets the boot log
compare the estimate against a real ceiling instead of a fixed `> 50`
guess, and warns above 80% of it.

## What was NOT changed

- `API_CLUSTER_WORKERS` itself — still unset everywhere, still defaults to
  `1`. Activating it in real production is an operator decision informed by
  the service's actual CPU allocation, which this phase does not have
  (`EER-04`, already logged as open in `docs/PERFORMANCE_INFRASTRUCTURE.md`,
  untracked on this machine — not re-opened here).
- `DB_POOL_MAX` / `API_DB_POOL_MAX` / `WORKER_DB_POOL_MAX` — not raised. Five
  independent measurements across this campaign (see
  `docs/PERFORMANCE_INFRASTRUCTURE.md`'s PERF-DB-001 entry) already
  concluded the pool was never the read-path constraint; P1.2/P1.3 below are
  the write-path follow-up, not a pool-size change either.

## Recommended values by vCPU tier

**Not measured on real production hardware this phase** — this table
applies the existing PERF-INFRA-003 measurement's scaling shape (roughly
linear improvement per added worker, diminishing after core count) and the
formula above; it is a starting point for an operator to validate against
the service's *actual* CPU allocation and Postgres's *actual*
`max_connections`, not a substitute for doing so.

| vCPU | `API_CLUSTER_WORKERS` | `API_DB_POOL_MAX` | `WORKER_DB_POOL_MAX` | Formula result | Needs `max_connections` ≥ |
|---|---|---|---|---|---|
| 1 | 1 (forking below the core count buys nothing — one event loop still shares the one core) | 15 (unchanged default) | 15 | 1×15×2+15 = 45 | ~60 (with headroom) |
| 2 | 2 | 10 | 15 | 2×10×2+15 = 55 | ~70 |
| 4 | 4 | 8 | 20 | 4×8×2+20 = 84 | ~110 |

**Lower `API_DB_POOL_MAX` per worker as worker count rises, don't hold it
fixed** — P0's own booking-path remediation measured each cluster worker's
real per-worker demand at only ~5 connections at peak (pool never exceeded
5 of 10 even under saturation, after the self-deadlock fix), so multiplying
a fixed pool size by worker count overstates real need; the table above
already reflects that by shrinking `API_DB_POOL_MAX` as `API_CLUSTER_WORKERS`
grows.

## What the operator needs to do before enabling this

1. **Read the real ceiling** (read-only): `SHOW max_connections;` against
   production Postgres, or via Railway's dashboard for a managed instance.
2. **Read the real CPU allocation** for the API service (Railway service
   settings or `docker inspect`'s `NanoCpus` if self-hosted) — this decides
   which row of the table above applies, and whether forking below the core
   count is worth doing at all (it is not, below ~2 cores).
3. Set `DB_MAX_CONNECTIONS` to the real value from step 1 so the boot log's
   comparison is precise, not a guess.
4. Set `API_CLUSTER_WORKERS`, `API_DB_POOL_MAX`, `WORKER_DB_POOL_MAX`
   informed by steps 1–2 and the table above.
5. Deploy, read the boot log's percentage, confirm it is comfortably under
   80%.

None of this was done by this phase — steps 1–2 require production access
this session does not have, and step 4 is a deployment configuration
change, which stays an explicit operator action per the standing rule for
this entire remediation.
